# 03 — 扫描引擎

扫描引擎的职责**只有一个**：产出关于文件系统的**事实**。它不判断「能不能删」——那是 `analyze/cleanability` 的工作。这条边界必须守住，否则规则知识会渗透进遍历代码，导致无法测试、无法复用。

---

## 1. 卷枚举

### 1.1 枚举方式

```go
// 1. 拿到所有盘符掩码
mask, err := winapi.GetLogicalDrives()

// 2. 逐个拿卷信息
for i := 0; i < 26; i++ {
    if mask&(1<<i) == 0 { continue }
    root := string(rune('A'+i)) + ":\\"

    // 关键：用 GetDriveTypeW 过滤
    switch winapi.GetDriveType(root) {
    case DRIVE_FIXED:       // 保留
    case DRIVE_REMOVABLE,   // 默认排除（U 盘扫了没意义且慢）
         DRIVE_REMOTE,      // 排除（网络盘）
         DRIVE_CDROM,       // 排除
         DRIVE_RAMDISK,     // 排除
         DRIVE_NO_ROOT_DIR:  // 排除（未挂载卷）
    }
}
```

### 1.2 卷元信息

| 字段 | 来源 | 坑 |
| --- | --- | --- |
| 卷标 | `GetVolumeInformationW` | 可能为空 |
| 文件系统 | `GetVolumeInformationW` 返回 `lpFileSystemName` | 判断是否 NTFS 是**迁移预检的必需项**（FAT32 不支持 >4 GB 文件与 reparse point） |
| 卷序列号 | `GetVolumeInformationW` 的 `lpVolumeSerialNumber` | 硬链接去重需要 `(VolumeSerial, FileIndex)` 组合 |
| 总容量 / 剩余 | `GetDiskFreeSpaceExW` | 注意用 64 位版本，别用 `GetDiskFreeSpace`（32 位溢出） |
| 簇大小 | `GetDiskFreeSpaceExW` 的 `lpBytesPerCluster` | 计算「实际占用」（簇对齐后）需要 |
| 是否 BitLocker | `Win32_EncryptableVolume` (WMI) | P2，只做提示 |

### 1.3 卷级别的危险判断

枚举时要顺便识别并**默认排除**：

- 系统保留分区（无盘符，通常扫不到）
- EFI 分区（同上）
- 恢复分区（同上）
- `System Volume Information`（快照/还原点，L0 禁删，遍历时直接跳过）

### 1.4 输出模型

```go
type Volume struct {
    Root          string        // "C:\"
    Letter        string        // "C"
    Label         string        // "Windows-SSD"
    FileSystem    string        // "NTFS"
    SerialNumber  uint32
    TotalBytes    uint64
    FreeBytes     uint64
    BytesPerCluster uint32
    DriveType     uint32
    IsSystem      bool          // 是否为操作系统所在盘
    IsBoot        bool
    Scanned       bool
}
```

## 2. 安全目录遍历（核心）

遍历代码是整个工具**最危险的部分**——写错了就会越界删除或重复计数。以下是必须遵守的规则。

### 2.1 规则 1：绝不跟随 reparse point

NTFS 的 reparse point 包括：

| Tag | 类型 | 例子 |
| --- | --- | --- |
| `IO_REPARSE_TAG_MOUNT_POINT` (0xA0000003) | 目录联接（Junction）/ 卷挂载点 | `mklink /J` |
| `IO_REPARSE_TAG_SYMLINK` (0xA000000C) | 符号链接 | `mklink /D` |
| `IO_REPARSE_TAG_CLOUD_*` (0x9000001A 等) | OneDrive 云占位文件 | 未下载的文件 |
| `IO_REPARSE_TAG_DEDUP` (0x80000013) | 数据去重 | 服务器场景 |
| `IO_REPARSE_TAG_APPEXECLINK` (0x8000001B) | UWP/Store 应用的执行链 | `WindowsApps` 下 |

**处理方式**：读取目录项时用 `FILE_FLAG_OPEN_REPARSE_POINT`，拿到 `dwFileAttributes & FILE_ATTRIBUTE_REPARSE_POINT` 后，再读取 reparse tag 分类：

```go
switch tag {
case IO_REPARSE_TAG_MOUNT_POINT, IO_REPARSE_TAG_SYMLINK:
    // 记录为「链接」，统计链接本身的 0 字节，不递归进去
    // 但要在报告里显式列出：「X 是一个指向 Y 的链接，未展开」
    node.Kind = NodeLink
    node.LinkTarget = readLinkTarget(handle)
    return  // 不递归

case IO_REPARSE_TAG_CLOUD_*:
    // OneDrive 占位文件：本地实际占用可能是 0
    // 必须分别统计 LogicalSize 与 OnDiskSize，否则会虚报空间
    node.IsCloudPlaceholder = true
    // 仍要统计，但标注

case IO_REPARSE_TAG_DEDUP:
    // 去重文件：OnDiskSize 是共享的，不能累加
    node.IsDeduped = true

default:
    // 未知 tag：保守起见不递归，记录告警
    log.Warn("unknown reparse tag", "tag", tag, "path", path)
    return
}
```

**为什么这条最重要**：如果跟随 reparse point，会发生两类灾难——(a) 一个 Junction 指向 `C:\Windows` 时，遍历会把整个 Windows 目录重复统计一遍；(b) 后续的清理/迁移算子在「规范化路径」时如果跟随链接，会把操作作用到链接目标上，删掉不该删的东西。**这条必须在 M1 就写对，不能留到后面补。**

本机实测：`C:\Users\33380\OneDrive` 是真实目录（非链接），但 OneDrive 会为未下载文件创建云占位。同时用户已手工把一些东西搬到 D 盘，很可能存在手工创建的 Junction，遍历时能发现这一点本身就是有价值的信息。

### 2.2 规则 2：长路径必须加 `\\?\` 前缀

Windows 默认 `MAX_PATH` 是 260。开发者的 `node_modules` 嵌套极易超过。

```go
func toExtendedPath(p string) string {
    if strings.HasPrefix(p, `\\?\`) { return p }
    if strings.HasPrefix(p, `\\`) {  // UNC
        return `\\?\UNC\` + p[2:]
    }
    // 必须转成绝对路径，反斜杠分隔
    abs, _ := filepath.Abs(p)
    return `\\?\` + abs
}
```

**注意**：`\\?\` 前缀会**禁用**路径规范化，`.`/`..`/正斜杠全都不再被解释。所以必须先 `filepath.Clean` 再转换。这个特性正好可以用于**路径安全校验**（见 `09-安全与风险控制.md`）。

### 2.3 规则 3：权限拒绝不是错误

普通用户无权读的目录（`C:\System Volume Information`、其他用户的 profile、部分 `ProgramData`）：

```go
entries, err := os.ReadDir(dir)
if err != nil {
    if errors.Is(err, fs.ErrPermission) {
        stats.SkippedDirs++
        stats.SkippedReasons = append(stats.SkippedReasons, SkippedDir{dir, "access denied"})
        return nil  // 不中断整个扫描
    }
    // 其他错误计入 Errors
}
```

报告末尾必须汇总，并提示「以管理员权限运行可获取完整结果」（FR：见 `01` FR-3）。

### 2.4 规则 4：硬链接只计一次（**实现方式与最初设计不同，见下方实测说明**）

同一物理文件可能有多个硬链接。实测本机情况比预想严重得多：

| 目录 | 逻辑大小 | 实际分配 | 差异 |
| --- | --- | --- | --- |
| `~\.cache\codex-runtimes` | 1127 MB | 768 MB | **-47%（硬链接）** |
| `C:\Windows\System32\kernel32.dll` | — | — | `NumberOfLinks = 2` |

判定硬链接需要「文件索引」。**最初的设想是通过目录枚举结果直接拿到，实测证明行不通**：

```
实测结论（见 internal/winapi/types.go 的 FileIndex 注释与 doctor 命令）：
· WIN32_FIND_DATA 中紧跟文件大小的两个 DWORD 是【保留字段】，
  无论 FindExInfoBasic 还是 FindExInfoStandard，实测恒为 0。
· 可靠的文件索引只能通过 GetFileInformationByHandle 获取，
  即需要【对每个文件打开一次句柄】。
· 因此硬链接去重无法在快速模式下完成，只能在 --deep 模式做。
```

实现方式（`internal/winapi/fileinfo.go`）：

```go
// 一次 CreateFile + 两次查询，同时得到文件索引与真实分配大小
h := CreateFile(path, FILE_READ_ATTRIBUTES, share, ..., FILE_FLAG_BACKUP_SEMANTICS)
GetFileInformationByHandle(h, &basic)              // → VolumeSerialNumber, FileIndex, NumberOfLinks
GetFileInformationByHandleEx(h, FileStandardInfo, &std)  // → AllocationSize
```

| 要点 | 说明 |
| --- | --- |
| 只需 `FILE_READ_ATTRIBUTES` | 不需要读数据权限，因此对只读文件、他人文件通常也能成功 |
| 云占位文件**不打开句柄** | 避免触发云文件下载（这一点是安全要求，不只是性能考虑） |
| 失败不致命 | 计入 `stats.file_id_errors` 并告警，退化为簇对齐估算 |
| 判定条件 | `NumberOfLinks > 1` 且 `FileIndex != 0` 才参与去重 |

**语义**：第一个遇到的链接计入全量占用，后续链接 `OnDisk` 计 0，
但**文件数仍逐条累加**（目录项计数不受影响）。因此 `Logical > OnDisk` 是正常的。

### 2.5 规则 5：`AllocationSize` 才是准确的实际占用（实测修正）

最初设计用「簇对齐估算」得到 `OnDisk`。实测发现两个 API 的真实语义与直觉不同：

| API | 对 49 字节文件 | 对 562 字节文件 | 对 91 MB 文件 | 结论 |
| --- | --- | --- | --- | --- |
| 簇对齐估算 | 4096 | 4096 | 91381760 | 对驻留文件**高估** |
| `FILE_STANDARD_INFO.AllocationSize` | **56** | **4096** | 91381760 | **准确** |
| `GetCompressedFileSize` | 49 | 562 | 91380224 | 对未压缩文件返回逻辑大小，**不反映簇对齐** |

- 49 字节报 56（按 8 字节对齐）：说明该文件**驻留于 MFT 记录内，不占簇**。NTFS 上小于约 700 字节的文件都是这种情况。
- 562 字节报 4096：说明它占了 1 个簇。
- 因此 `AllocationSize` 能正确区分「驻留」与「占用簇」，是唯一准确的来源。

**`GetCompressedFileSize` 的定位修正**：它只对稀疏/压缩/云占位文件返回小于逻辑大小的值，对普通文件返回逻辑大小。
所以它**不是**通用的「磁盘上的大小」API，不能作为 `OnDisk` 的来源。
它的正确用途是**云占位文件**——那类文件不能打开句柄（会触发下载），而它只读元数据，是安全的选择。

### 2.6 规则 6：重解析点的 `PathBuffer` 偏移随类型而变（实测修正）

`REPARSE_DATA_BUFFER` 的布局对两种类型**不同**：

```
MOUNT_POINT（目录联接/Junction）:              PathBuffer @ 16
  tag(4) dataLen(2) reserved(2) subOff(2) subLen(2) printOff(2) printLen(2)

SYMLINK（符号链接）:                           PathBuffer @ 20
  tag(4) dataLen(2) reserved(2) subOff(2) subLen(2) printOff(2) printLen(2) flags(4)
                                                                           ↑ 多这个 DWORD
```

用 16 去读符号链接会**错位**。实测复现：`C:\Users\All Users` 的目标读成 `ta\??\C:\ProgramDa`
（多了前缀 `ta`、尾部少了 `ta`）——因为偏移 44 恰好落在 `C:\ProgramData` 的最后两个字符上。

回归测试：`internal/winapi/reparse_layout_test.go`
- `TestReparseLayoutOnJunction` 用 `mklink /J` 建真实联接验证
- `TestDumpSystemSymlink` 用系统自带的兼容性软链验证（无需提权）


### 2.7 规则 7：目录项读取用 `FindFirstFileExW` 而非 `os.ReadDir`

`os.ReadDir` 只返回文件名，之后对每个文件 `os.Stat` 会产生 N 次系统调用。`FindFirstFileExW` 一次调用就返回目录下所有条目的完整元数据（大小、时间、属性），性能差一个数量级。

```go
// FIND_FIRST_EX_LARGE_FETCH 显著提升大目录的批量读取效率
data := winapi.Win32FindData{}
h, err := winapi.FindFirstFileEx(          // 内部调 FindFirstFileExW
    sys.ToExtendedPath(joinChild(dir, "*")),   // 必须是 \\?\ 前缀 + 以 \* 结尾
    // 用 FindExInfoStandard：不能指望枚举结果给出文件索引
    // （FindExInfoBasic 也一样不填，实测两个 DWORD 恒为 0，见规则 4）
    winapi.FindExInfoStandard,
    &data,
    winapi.FindExSearchNameMatch,
    0,
    winapi.FIND_FIRST_EX_LARGE_FETCH,
)
```

**坑**：
- 路径必须以 `\*` 结尾，否则行为不同；且必须加 `\\?\` 前缀（规则 2）。
- 它在**空目录**上返回 `ERROR_FILE_NOT_FOUND`——这不是错误，必须当作空目录处理，
  否则每个空目录都会计入 `errors`，报告里出现大量假错误。
- 它不解析 reparse point 的内容，这正好符合规则 1——链接的目标需要额外
  `CreateFile(FILE_FLAG_OPEN_REPARSE_POINT)` + `FSCTL_GET_REPARSE_POINT` 来读。
- 文件名是 UTF-16，且 `.`/`..` 也会返回。判断这两个特殊项时应直接比较原始
  UTF-16 数组，避免为每个条目做一次字符串转换（百万级条目下差异可观）。

### 2.8 规则 8：`LogicalSize` 与 `OnDiskSize` 分开统计

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| `LogicalSize` | 文件声明的字节数 | 用户直觉的「多大」 |
| `OnDiskSize` | 实际占用簇（`((size + cluster - 1) / cluster) * cluster`） | 真实释放多少空间 |
| `SparseSize` | 稀疏文件的实际分配 | 虚拟机磁盘（VHDX）常见，二者差异巨大 |
| `CloudPlaceholder` | OneDrive 未下载文件 | 本地占用 ≈ 0 但 `LogicalSize` 很大 |

**为什么必须分开**：如果只报 `LogicalSize`，用户会看到 Docker 的 `ext4.vhdx` 报 100 GB，但实际本地可能只有 20 GB；反之 OneDrive 占位文件会虚报大量空间。报告的「能释放 X GB」必须基于 `OnDiskSize`。

### 2.9 规则 9：时间戳要读三个

`WIN32_FIND_DATA` 提供三个时间，语义不同，用途也不同：

- `ftLastWriteTime` —— **判断「多久没动过」用这个**（临时文件年龄过滤的基础）
- `ftCreationTime` —— 创建时间
- `ftLastAccessTime` —— 访问时间，**默认分区上被禁用**（`NtfsDisableLastAccessUpdate`），不可靠，不要用

## 3. 空间统计与聚合

### 3.1 流式聚合，不全量驻留

详见 `02` 的并发模型。要点：

```
worker                        aggregator (单 goroutine)
  │                                │
  │ 遍历目录，产出 DirStat           │
  ├───────────────────────────────►│
  │   {Path, Files, Logical, Disk,  │  维护 map[path]*Agg
  │    MtimeMin, MtimeMax, Subdirs} │  按深度保留或丢弃
  │                                │
  │                                ├─► 深度 ≤ maxDepth：保留节点
  │                                └─► 命中规则/命名模式：保留节点
  │                                   其余：只累加到父节点数值
```

### 3.2 自底向上回传

由于是并发遍历，不能简单地「边遍历边累加到父目录」（父目录可能已经遍历完了）。做法：每个目录遍历完成时，把 `DirStat` 发给 aggregator，aggregator 按路径深度**降序**处理，依次把子目录数值累加到父目录。这样父目录数值在最后一刻才确定。

### 3.3 报告阈值

默认 `--min-size 10MB`：只把 ≥10 MB 的目录作为独立条目上报。避免报告被成千上万个几 KB 的目录淹没。但**累加不受阈值影响**——父目录的总量永远准确。

## 5. 两种模式

| 模式 | 命令 | 行为 | 实测耗时（本机 C 盘，143.9 万文件 / 40.7 万目录） |
| --- | --- | --- | --- |
| **快速模式** | `scan`（默认） | 只按簇对齐估算占用；不做硬链接去重（需要逐文件句柄）；`MaxDepth` 只影响上报粒度 | **45 秒** |
| **深度模式** | `scan --deep` | 逐文件读取真实分配大小 + 硬链接去重；读重解析点详情 | 预计 3–7 分钟（待实测） |
| **定点模式** | `scan --path <dir>` | 只扫指定目录，全深度 | 秒级（2.6 万文件约 1 秒） |

**关于 `MaxDepth` 的语义（实测后明确）**：它**不是遍历深度，而是上报粒度**。

遍历始终是全深度的，因为父目录的总量必须包含所有后代。若为了「快」而在 `MaxDepth` 处停止遍历，
父目录的大小就会偏小——而一个偏小的总量会让用户误以为系统盘还有空间，**这比慢更危险**。

因此「快速」与「深度」的区别不体现在遍历深度上，而体现在**是否为每个文件打开句柄**：

| | 快速模式 | 深度模式 |
| --- | --- | --- |
| 目录枚举 | ✅ | ✅ |
| 打开文件句柄 | ❌ | ✅（每文件 1 次 CreateFile + 2 次查询） |
| 实际占用来源 | 簇对齐估算 | `FILE_STANDARD_INFO.AllocationSize` |
| 硬链接去重 | ❌（明确告警） | ✅ |
| 重解析点目标解析 | 目录级 | 目录级 + 文件级 |

### 5.1 实测性能与并行度

| 线程数 | 耗时 |
| --- | --- |
| 8 | 49.2s |
| **16** | **45.4s** |
| 32 | 56.2s |

**16 线程最优**，且并行度收益有限（8→16 仅提升 8%，32 反而变慢）。
这**不是** CPU 瓶颈，最可能的原因是杀毒软件的实时防护在每个目录枚举上做拦截检查。
这类外部因素无法通过优化代码消除。

优化历程（98s → 45s）：

| 优化 | 说明 |
| --- | --- |
| 按目录批量刷新统计 | 原先每文件 4 次全局原子自增，16 个 worker 争同一组缓存行；改为每目录刷新一次，原子操作次数降两个数量级 |
| top-N 无锁阈值筛选 | 原先每个文件都要争一次互斥锁并分配 `time.Time`；改为先用只增不减的原子阈值筛选 |
| 预转小写前缀 | `isSummaryOnly`/`isExcluded` 对每个目录都要查，原先内部做 `ToLower` 导致数百万次字符串分配 |
| 延迟文件名转换 | 快速模式下的普通文件只需要大小/属性/时间戳，不需要路径字符串 |
| `.`/`..` 判断 | 直接比较 UTF-16 数组，避免为每个条目做字符串转换 |

**未来的数量级优化**：改用 NTFS 的 MFT 枚举（`FSCTL_ENUM_USN_DATA`）可以一次拿到全部文件元数据，
速度提升一个数量级，但需要管理员权限打开卷句柄（`\\.\C:`），与本工具「扫描不需要提权」的前提冲突。
列为后续可选项，不作为默认路径。

## 6. 进度反馈与中断

```
$ winclean scan --disk C
扫描 C:\ ... [=====================>    ] 78%  61.2万文件 / 24.8GB / 跳过 312 目录  (12.4s)
```

- 更新频率限制在 **≤ 10 Hz**（否则刷屏影响性能）
- 只在 stderr 且是 TTY 时输出；非 TTY（管道/重定向）时自动禁用，避免污染 `--format json` 的输出
- Ctrl+C → cancel context → worker 退出 → aggregator 收尾 → 输出已完成部分 → 退出码 130

## 7. 性能预算与优化手段

| 手段 | 收益 |
| --- | --- |
| `FindFirstFileExW` 批量读目录项 | 减少 1–2 个数量级 syscall |
| `FIND_FIRST_EX_LARGE_FETCH` | 机械盘/大目录批量读提升明显 |
| worker pool 并发 | 吃满 SSD 队列深度 |
| 小文件跳过 FileIndex 去重 | 省大量内存 |
| 目录数超阈值后停止细分 | 防止 `node_modules` 拖垮 |
| 单聚合 goroutine | 免锁，减少竞争 |
| `--min-size` 抑制上报量 | 减少报告层与内存开销 |
| 避免 `filepath.Walk`（标准库） | 它每层都 `Lstat` + `ReadDir`，且不控 reparse |

**反模式（明确不用）**：
- 用 `filepath.Walk` / `filepath.WalkDir` —— 无法控制 reparse point 行为，且拿不到 FileIndex / OnDiskSize
- 每文件一次 `os.Stat` —— syscall 数量爆炸
- 先把整棵树建成 struct 再统计 —— 内存不可控

## 8. 扫描结果的自校验

扫描完成后、交给分析层之前，做一次一致性检查（断言，失败即 bug）：

```go
// 1. 子目录之和 + 直属文件之和 == 父目录总量（除跳过部分）
// 2. 磁盘上所有卷的已用量之和 <= 卷总容量 - 卷剩余（留容差，因为跳过与权限）
// 3. 无重复路径节点
// 4. 所有路径均为绝对路径且已 Clean
// 5. 统计到的总占用与「卷总量 - 剩余」的偏差 > 15% 时输出告警
//    （提示：可能有未扫描区域/权限不足/存在其他用户 profile）
```

第 5 条特别有用——它能立刻暴露「扫描不完整」，避免用户基于残缺数据做决策。
