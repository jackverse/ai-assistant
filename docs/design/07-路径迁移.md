# 07 — 路径迁移

回答「怎么把东西搬到非 C 盘」。

**设计前提（来自实测）**：本机可回收空间里，**迁移占 66 GB，是绝对主力**（删除只占 2–3 GB）。所以这篇文档的地位等同于「清理」在传统工具中的地位，不是附加功能。

---

## 1. 核心认知：「改路径」不是一种操作，而是六种完全不同的机制

这是最容易做错的地方。把「把 Chrome 数据搬到 D 盘」和「把页面文件搬到 D 盘」当成同一件事，会写出灾难性的代码——它们从原理到权限到回滚方式全都不同。

| # | 机制 | 原理 | 适用 | 权限 | 可回滚 | 软件感知 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **目录联接 / 符号链接（Junction）** | 把目录搬到新位置，在**原位置**留一个 NTFS 重解析点 | 任意目录，**不需要软件支持** | Junction 不需要提权；Symlink 需要（或开发者模式） | ✅ 删链接 + 搬回 | **无感知**（路径看起来没变） |
| 2 | **应用自身配置** | 改软件自己的设置项 | 软件支持时**最优** | 通常不需要 | ✅ 改回配置 | 完全支持（官方途径） |
| 3 | **环境变量** | 改 `NPM_CONFIG_CACHE` 等，软件按变量找路径 | 开发工具、运行时 | 用户级不需提权（写 `HKCU\Environment`） | ✅ 改回 | 需重启进程才生效 |
| 4 | **Known Folder 重定向** | 改系统「下载/文档」等文件夹位置 | 系统已知文件夹 | 不需要（用户级） | ✅ 官方支持反向操作 | 系统级支持，但**部分软件硬编码路径会失效** |
| 5 | **注册表指向** | 改软件自己存的路径键值 | 部分软件（微信、Steam） | 视键位置 | ✅ | 软件读注册表 |
| 6 | **虚拟磁盘迁移** | 把 `.vhdx` 移到别的盘并在软件里改指向 | Docker Desktop、WSL2、Hyper-V | Docker：不需提权（GUI 设置）；Hyper-V：需提权 | ✅ 官方支持 | 软件原生支持 |
| 7 | **系统设置调整** | 页面文件移到别的盘、关闭休眠 | `pagefile.sys` / `hiberfil.sys` | **需提权** | ✅ 可逆 | 系统级 |
| — | ~~重装 / 移动已安装程序~~ | — | — | — | — | **不做**（见 §8） |

### 1.1 机制选择的决策树

```
该路径有官方支持的位置设置吗？
├─ 是（Docker Desktop「Disk image location」、微信「文件管理」、Steam 库文件夹）
│   → 机制 2/6：应用自身配置        ★ 最优，优先选它
│
├─ 是环境变量控制的吗？（npm/pip/yarn/nvm/gradle/go/android-sdk）
│   → 机制 3：环境变量              ★ 次优，官方且干净
│
├─ 是系统 Known Folder 吗？（下载/文档/图片/桌面）
│   ├─ 被 OneDrive 接管？ → ✖ 不动（会破坏同步）
│   └─ 未被接管？        → 机制 4：Known Folder 重定向
│
├─ 是虚拟磁盘（.vhdx）吗？
│   → 机制 6：在宿主软件里改指向
│
├─ 是页面文件 / 休眠文件吗？
│   → 机制 7：系统设置调整（需提权）
│
├─ 软件把路径存在注册表里吗？
│   → 机制 5：注册表
│
└─ 以上都不适用
    → 机制 1：Junction 作为通用兜底    ★ 万能但需谨慎
```

**关键原则**：**能用官方机制就绝不用 Junction。** Junction 是兜底方案，不是首选。原因：官方机制是软件"知道"的状态（升级、修复、诊断都不会出问题），而 Junction 是"骗"软件——绝大多数情况下没问题，但在软件做完整性检查、走原生代码（非 Win32 路径 API）、或涉及安全边界时可能出问题。

对本机的具体映射：

| 路径 | 大小 | 应采用机制 | 理由 |
| --- | --- | --- | --- |
| `docker_data.vhdx` | 36.0 GB | **6 虚拟磁盘迁移** | Docker Desktop 官方支持 |
| `Yarn\Cache` | 8.2 GB | **3 环境变量**（`YARN_CACHE_FOLDER`） | Yarn 官方支持 |
| `Android\Sdk` | 5.1 GB | **3 环境变量**（`ANDROID_SDK_ROOT`） | 官方支持 |
| `.m2\repository` | 3.0 GB | **2 应用配置**（`settings.xml` 的 `localRepository`） | Maven 官方支持 |
| `.cache`（puppeteer 等） | 3.5 GB | **1 Junction** + 部分环境变量 | 各工具变量不统一，Junction 兜底 |
| `nvm` | 2.0 GB | **3 环境变量**（`NVM_HOME`） | nvm 官方支持 |
| `pagefile.sys` | 24.3 GB | **7 系统设置** | 需提权 |
| `hiberfil.sys` | 9.7 GB | **7 系统设置** | `powercfg /h off` |
| `pip\Cache` | 0.31 GB | **3 环境变量**（`PIP_CACHE_DIR`） | |

## 2. Junction 详解（主力兜底方案）

### 2.1 为什么 Junction 优于 Symlink

| | **Junction** (`IO_REPARSE_TAG_MOUNT_POINT`) | **Symbolic Link** (`IO_REPARSE_TAG_SYMLINK`) |
| --- | --- | --- |
| 创建权限 | **普通用户即可**（本地卷内） | 需管理员或开发者模式 |
| 目标 | **只能是本地绝对路径目录** | 可文件可目录，可相对，可 UNC |
| 跨盘符 | ✅ 支持 | ✅ 支持 |
| 删除链接 | 只删链接，**不影响目标内容**（用 `RemoveDirectory`） | 同 |
| 兼容性 | 极好（Windows 2000 起） | 部分老程序不认 |
| 网络路径 | ❌ 不支持 | ✅ 支持 |

**选择 Junction**：不需要提权这一点是决定性的——用户不必每次迁移都提权，且迁移失败的风险面更小。局限是不能指向 UNC（网络盘），这对本场景无影响。

### 2.2 创建方式

Go 标准库 `os.Symlink` 在 Windows 上创建的是 **Symlink**（需要提权），**不能用于 Junction**。必须走 `DeviceIoControl`：

```go
// 1. 创建目标目录
os.MkdirAll(target, 0755)

// 2. 创建空的原目录（Junction 的挂载点必须存在且为空）
os.Mkdir(source, 0755)

// 3. 用 FSCTL_SET_REPARSE_POINT 写入
// 难点：路径必须用 NT 命名空间格式 \??\C:\path，而不是 Win32 格式 C:\path
ntTarget := `\??\` + target            // 绝对路径，无 \\?\ 前缀

rsd := REPARSE_DATA_BUFFER{
    ReparseTag:        IO_REPARSE_TAG_MOUNT_POINT,
    ReparseDataLength: uint16(8 + len(ntTargetUtf16)*2 + len(printNameUtf16)*2),
    MountPointReparseBuffer: {
        SubstituteNameOffset: 0,
        SubstituteNameLength: uint16(len(ntTargetUtf16) * 2),
        PrintNameOffset:      uint16(len(ntTargetUtf16)*2 + 2),
        PrintNameLength:      uint16(len(printNameUtf16) * 2),
    },
}
// 拼接 SubstituteName + \0 + PrintName + \0
// DeviceIoControl(handle, FSCTL_SET_REPARSE_POINT, &rsd, ...)
```

**坑清单**：
- `SubstituteName` 必须是 `\??\X:\...` 格式（NT 命名空间），写成 `X:\...` 会用不了
- `PrintName` 是给用户看的目标路径，用 Win32 格式
- 全部字符串是 **UTF-16LE**，长度以**字节**计（不是字符数）
- 挂载点目录必须**已存在且为空**，否则返回 `ERROR_ALREADY_EXISTS` 或 `ERROR_DIR_NOT_EMPTY`
- 结构体必须按 8 字节对齐（`REPARSE_DATA_BUFFER` 有 `DWORD` 对齐要求）

### 2.3 Junction 的风险与限制

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **软件不认 reparse point** | 少数软件（尤其自己解析路径、做完整性校验、或用非 Win32 API 的）会出问题 | 预检时优先尝试官方机制；Junction 作为兜底并在报告里标注「非官方方式」 |
| **备份/同步工具会跟随链接** | Windows 备份、`robocopy /S`（默认不跟随，但 `/SJ` 会）、OneDrive 可能把目标内容再同步一遍 | 报告中警告；避免对 OneDrive 同步范围内的目录用 Junction |
| **可能造成循环** | 若链接目标又是链接，或目标在链接内部，遍历会死循环 | 创建前解析目标，确保不在自身子树内；遍历时限制 reparse 深度 |
| **删除链接时误删目标** | 用 `os.RemoveAll` 会**递归进目标**并删掉真实数据！ | **必须**用 `RemoveDirectory`（只删链接本身）；这是高危点，见 §4.4 |
| **跨盘符移动大目录耗时长** | 36 GB 的 VHDX 复制需要时间 | 进度反馈；可中断可续；先复制后删 |
| **权限继承** | 新位置可能继承不同的 ACL | 复制后用 `CopyFile` 保留属性，或显式设置 ACL |

### 2.4 Junction 的识别与遍历

见 `03` §2.1。要点回顾：读取时 `FILE_FLAG_OPEN_REPARSE_POINT`，tag `IO_REPARSE_TAG_MOUNT_POINT` → 是 Junction。**遍历不递归进去**，且**绝不对链接本身生成删除动作**。

## 3. 迁移算子标准流程（七步，一步都不能省）

无论用哪种机制，底层动作序列是固定的。**绝不用 `Move`/`rename`**——跨盘 move 非原子，中途失败会丢数据。

```
┌─ 步骤 1：预检（Precheck）—— 不通过就不允许执行 ────────────────────────┐
│  · 源路径存在、是目录（或预期的文件）、可访问                              │
│  · 源路径**不是** reparse point（否则要先处理链接本身）                    │
│  · 目标盘存在、文件系统为 **NTFS**（FAT32/exFAT 不支持 reparse point）    │
│  · 目标盘剩余空间 >= 源大小 × 1.1（留 10% 余量）                          │
│  · 目标路径**尚不存在**（若存在→报错，绝不覆盖）                           │
│  · 目标路径不在源的子树内（防循环）                                        │
│  · 目标路径长度 < 260 或已确认支持长路径                                   │
│  · 无进程占用源目录下的文件（否则可能复制出不完整/不一致的快照）             │
│  · 无软件正在运行（可选，强建议：如迁移 Docker 时 Docker Desktop 需停止）    │
│  · 权限：是否有权创建 Junction / 改环境变量 / 改页面文件                    │
└──────────────────────────────────────────────────────────────────────┘
                                  ▼
┌─ 步骤 2：复制（Copy）──────────────────────────────────────────────┐
│  · 用 `CopyFileEx`（可带进度回调）/ `SHFileOperation`（保留 ACL）      │
│  · 保留：文件属性、时间戳、ACL（关键！否则软件可能无权访问）              │
│  · 复制**不做移动**，源目录在验证通过前**保持原样**                     │
│  · 失败可安全重试 / 续传                                              │
└──────────────────────────────────────────────────────────────────────┘
                                  ▼
┌─ 步骤 3：校验（Verify）─────────────────────────────────────────────┐
│  · 文件数一致                                                       │
│  · 总逻辑大小一致                                                    │
│  · （可选，--verify-hash）抽样或全量哈希比对                          │
│  · 逐个抽查关键文件的 ACL 与 mtime                                     │
│  · 校验失败 → 中止，保留源，清理目标，报告失败原因                       │
└──────────────────────────────────────────────────────────────────────┘
                                  ▼
┌─ 步骤 4：切换（Switch）────────────────────────────────────────────┐
│  按机制分支：                                                        │
│  · Junction      → 删空的原目录 + 创建 Junction 指向新位置             │
│  · 环境变量      → 写新值（HKCU\Environment 或 HKLM）+ 广播 WM_SETTINGCHANGE │
│  · 应用配置      → 改配置文件/注册表项（需先停应用）                     │
│  · Known Folder  → SHSetKnownFolderPath + 移动文件                   │
│  · 虚拟磁盘      → 在宿主软件里改指向（部分需先停服务）                   │
│  · 系统设置      → 改页面文件配置 / powercfg                          │
│  ★ 关键：切换前把「原状态」写入 journal，供回滚                          │
└──────────────────────────────────────────────────────────────────────┘
                                  ▼
┌─ 步骤 5：验证生效（Validate）───────────────────────────────────────┐
│  · 原路径可访问且指向新位置（读一个已知文件/列目录）                       │
│  · 应用相关：尝试启动/查询（如 `docker info`、`node -v`、`yarn cache dir`）│
│  · 写入一个测试文件验证可写（有些软件需要写权限）                          │
└──────────────────────────────────────────────────────────────────────┘
                                  ▼
┌─ 步骤 6：延迟清理源（Deferred Purge）───────────────────────────────┐
│  · **默认不清理**！只标记「源目录待清理」，交由用户显式确认                 │
│  · 若清理：仅删除「已验证为链接/空目录」的原位置，不动目标                 │
│  · 提供 `--purge-source` 显式开关                                    │
│  · 对 Junction 机制：源位置已被链接取代，源数据在步骤 2 已复制到目标，      │
│    此处删除的是「复制前的原目录」——必须确保删的是链接不是目标（见 §4.4）    │
└──────────────────────────────────────────────────────────────────────┘
                                  ▼
┌─ 步骤 7：记账（Journal）──────────────────────────────────────────┐
│  · 记录：算子类型、源、目标、机制、时间、前后值、校验结果、可回滚信息         │
│  · journal 是 `apply` 的产物，`undo` 的输入                            │
│  · 每步都要落盘（fsync），不能只在内存里攒着——崩溃后要能恢复              │
└──────────────────────────────────────────────────────────────────────┘
```

**为什么「延迟清理」是默认行为**：因为「复制完成 + 校验通过」并不等于「软件真的能用新位置」。最安全的做法是让用户在真机上验证几天，确认一切正常后再删旧数据。代价是临时占用双份空间——对于 `C:` 只剩 3.9 GB 的用户，这在 Docker 36 GB 的场景下不可行，所以**必须为「空间不足以双份」提供一条显式路径**：允许在预检通过 + 校验通过后立即清理源，但要在报告里明确警告「无法回滚到旧位置的数据，只能回滚配置」。

这是一个**必须让用户显式决策的取舍**，不能由工具默默决定。

## 4. 高危点（必须专门防护）

### 4.1 目标盘空间不足

36 GB 的 VHDX 复制需要 D 盘有 40 GB 空闲（本机有 263 GB，OK）。但若用户选了个快满的盘，中途空间耗尽会留下半个目录。预检必须严格校验，且**保留 10% 余量**。

### 4.2 跨文件系统

目标是 FAT32/exFAT（如某些移动硬盘）→ **不支持 reparse point**，Junction 机制直接不可用。且 FAT32 单文件上限 4 GB，`docker_data.vhdx` 36 GB 根本放不下。预检必须检查文件系统 AND 单文件大小限制。

### 4.3 长路径

目标路径可能超过 260 字符（尤其带中文的深层路径）。检测并按需使用 `\\?\` 前缀。

### 4.4 ★ 删除链接时误删目标（最危险）

**这是整个工具最危险的单个操作。** `os.RemoveAll` 在遇到 Junction 时会**递归进入链接目标**并删除真实数据。

```go
// ❌ 灾难代码：如果 source 是 Junction 指向 D:\Data，这会删光 D:\Data
os.RemoveAll(source)

// ✅ 正确：RemoveDirectory 只删除重解析点本身，不触碰目标
winapi.RemoveDirectoryW(toExtendedPtr(source))

// ✅ 更安全：删除前先断言它确实是 reparse point
tag, err := readReparseTag(source)
if err != nil || !isReparsePoint(tag) {
    return fmt.Errorf("拒绝删除：%s 不是重解析点，可能是真实目录！", source)
}
winapi.RemoveDirectoryW(toExtendedPtr(source))
```

**防护措施**：
1. 删除任何 reparse point 前，**必须重新读取并确认其 tag**，不能依赖之前缓存的结果
2. 代码评审时把 `os.RemoveAll` 列入**禁用 API 清单**（在 CI 里 grep 检查）
3. 测试必须覆盖：建 Junction → 调用删除 → 断言目标内容完好

### 4.5 环境变量改了但不生效

写 `HKCU\Environment` 后：
- **已运行的进程不会感知**（它们持有旧环境块）→ 必须提示用户重启相关程序/终端
- 需要通过 `SendMessageTimeout(HWND_BROADCAST, WM_SETTINGCHANGE, 0, "Environment", ...)` 广播，让 Explorer 等刷新
- 已打开的 CMD/PowerShell 窗口不会自动更新

工具应当在迁移后**显式验证**并给出提示：

```
✅ 已设置 YARN_CACHE_FOLDER=D:\dev\yarn-cache
   ⚠️ 已打开的终端不会自动生效，请新开一个终端窗口
   ⚠️ 请确认没有正在运行的 yarn 进程
```

### 4.6 页面文件迁移的特殊性

| 项 | 说明 |
| --- | --- |
| 不能完全删掉 C 盘的页面文件 | 若 C 盘页面文件为 0，系统**无法生成崩溃转储**（蓝屏诊断需要）。建议 C 盘保留 2–4 GB 或设为「系统管理」的最小值 |
| 需提权 | `Win32_PageFileSetting` / 注册表 `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Memory Management` 的 `PagingFiles` |
| 需重启才生效 | 必须明确告知 |
| 注册表值格式 | `D:\pagefile.sys 4096 8192`（路径 + 初始大小 MB + 最大大小 MB） |
| 回滚 | 改回 `C:\pagefile.sys` 的值（journal 记录原值） |
| 风险 | 如果 D 盘是慢速机械盘/外置盘，系统性能可能下降；如果 D 盘是 SSD 则无影响 |

### 4.7 关闭休眠的副作用

`powercfg /h off` 会同时关闭 **快速启动（Fast Startup）**，笔记本用户会感知到开机变慢。必须在建议里说明。可逆（`powercfg /h on`），但 `hiberfil.sys` 会重新按内存大小生成（本机 9.7 GB，内存约 24 GB → 关闭后若想保留快速启动但缩小文件，可用 `powercfg /h /size 40` 把文件压到内存的 40%）。

**这三个选项要并列呈现**：
1. 完全关闭休眠 → 省 9.7 GB，失去休眠 + 快速启动
2. 缩小休眠文件（`powercfg /h /size 40`）→ 省约 4 GB，保留快速启动，失去休眠
3. 不动

## 5. 各类目标的具体迁移方案

### 5.1 Docker VHDX（36.0 GB，最大单项）

```
机制：6 虚拟磁盘迁移（Docker Desktop 官方支持）
步骤：
  1. 确认 Docker Desktop 已退出（托盘图标 → Quit Docker Desktop）
  2. 确认 WSL 已停止：`wsl --shutdown`
     （Docker Desktop 停止后 WSL2 后端可能仍在运行，必须显式关闭）
  3. 目标：D:\Docker\data\docker_data.vhdx
  4. 方式 A（推荐）：Docker Desktop → Settings → Resources → Advanced
                   → "Disk image location" 改为 D:\Docker\data → Apply
     Docker 会自己搬（这是官方机制，最安全）
  5. 方式 B（手动，当 GUI 不可用时）：
     复制 VHDX → 改 %APPDATA%\Docker\settings-store.json 里的
     "DataFolder" / "DiskPath" 字段 → 启动 Docker 验证
  6. 验证：`docker info` 能看到原有镜像；`docker images` 列表不变
风险：中（必须停服务；若 Docker 正在有容器运行，需先停止）
回滚：改回原路径
额外收益：
  `docker system prune -a --volumes` 后执行压缩
  （VHDX 是动态扩展的，删除镜像后文件不会自动变小，空洞可达数十 GB）
  压缩方式：需 Hyper-V 模块 `Optimize-VHD -Path <vhdx> -Mode Full`
            或 diskpart: select vdisk file=... / attach vdisk readonly / compact vdisk
```

> **注意**：`Optimize-VHD` 需要启用 Hyper-V 功能（Docker Desktop 用的是 WSL2 后端，可能未装 Hyper-V 管理模块）。替代是 `diskpart` 的 `compact vdisk`，或先把 VHDX 挂到某个 WSL 发行版内做 `fstrim` + `e2fsck`。这是**需要调研确认**的技术点，列入 M6 的风险项。

### 5.3 Android SDK（5.1 GB）

### 5.5 用户 Temp（0.29 GB，但机制值得推广）

```

目标：D:\Temp
```

### 5.6 `~/.cache`（3.5 GB）

这里的困难是**变量不统一**：puppeteer 用 `PUPPETEER_CACHE_DIR`，而 `codex-runtimes`、`chrome-devtools-mcp`、`opencode` 各自实现不同（有的读 `XDG_CACHE_HOME`，有的硬编码）。

```
机制：1 Junction（兜底）或逐个环境变量
方案 A（推荐）：对 ~/.cache 整体建 Junction → D:\dev\cache
   ⚠️ 但 XDG_CACHE_HOME 若被某些工具读取，需一并设置，否则不一致
方案 B：逐个工具设置其专属变量
   PUPPETEER_CACHE_DIR / XDG_CACHE_HOME
风险：低（缓存丢失只是重下）
注意：Junction 后 ~/.cache 路径不变但指向 D 盘，工具无感知
```

### 5.7 Known Folder 重定向（下载目录）

```
机制：4 Known Folder
目标：D:\Downloads
步骤：
  1. 读取当前值（本机 C:\Users\33380\Downloads，未重定向 ✅）
  2. 检测 OneDrive 接管（本机 Downloads 未被接管 ✅，但 Desktop/Pictures 已被接管 → 排除）
  3. 移动文件 + 写注册表（HKCU\...\User Shell Folders 的 {374DE290-...}）
     + 调 SHSetKnownFolderPath（更规范，会自动处理注册表与广播）
  4. 验证：SHGetKnownFolderPath 返回新值
风险：低 ——— 下载目录是最安全的 Known Folder 重定向目标
不做：Desktop / Documents / Pictures（本机 Desktop 与 Pictures 已被 OneDrive 接管，
      强行改会破坏 OneDrive 同步；Documents 虽未接管但很多软件硬编码
      %USERPROFILE%\Documents，风险高）
```

## 6. 预检产出与风险等级

```go
type PrecheckResult struct {
    Passed          bool
    Checks          []PrecheckItem
    RequiredAdmin   bool
    RequiredRestart bool      // 是否需要重启系统/软件
    DiskSpaceNeeded int64
    DiskSpaceAvail  int64
    Blockers        []string  // 阻断项
    Warnings        []string  // 警告项（不阻断但需用户知晓）
}

type PrecheckItem struct {
    Name    string   // "target_is_ntfs" / "no_process_using_source" / ...
    Passed  bool
    Level   string   // "blocker" / "warning" / "info"
    Detail  string
}
```

风险等级（用于报告排序与默认勾选）：

| 等级 | 判据 | 默认勾选 |
| --- | --- | --- |
| **低** | 官方机制 + 无需提权 + 无需停服务 + 非系统路径 | ✅ |
| **中** | 需提权 / 需停服务 / 会影响其他项目（如 Android SDK）/ 涉及环境变量生效延迟 | ❌（需用户确认） |
| **高** | 只能用 Junction 且软件敏感 / 涉及用户数据 / 无法完整回滚（受空间限制） | ❌（需逐项确认 + 提示备份） |

## 7. 回滚（undo）

undo 依赖 journal：

```go
type JournalEntry struct {
    ID          string
    Timestamp   time.Time
    Operator    OperatorType    // migrate-env / migrate-junction / migrate-appconfig / change-setting
    Source      string
    Target      string
    Mechanism   Mechanism
    PrevState   PrevState       // 关键！用于恢复
    VerifyState VerifyState     // 校验结果
    Result      string          // success / failed / partial
}

type PrevState struct {
    EnvVarOldValue   *string   // 环境变量原值（nil = 原本不存在）
    RegistryOldValue *RegValue
    JunctionExisted  bool      // 原本是否已是链接
    KnownFolderOld   string
    PageFileOld      string    // "C:\pagefile.sys 4096 8192"
    HibernateWasOn   bool
}
```

undo 的规则：
- **能恢复配置**：环境变量、注册表、Known Folder、页面文件、休眠 → 可完整恢复
- **数据搬不回来**：如果源已被清理且目标盘空间不足以搬回，则只能恢复配置指向原路径——而原路径已空。**这时必须报错并让用户手动处理，不能静默失败**
- **Junction 的 undo**：删链接 → 把目标目录搬回原位置 → 验证。若空间不足则中止并保留现状

## 8. 明确不做的迁移

| 不做 | 原因 |
| --- | --- |
| 移动已安装的程序（`Program Files` 下的软件） | 需要改注册表大量路径 + 服务 + 快捷方式 + COM 注册，没有任何通用可靠方案。正确做法是卸载重装到新盘 |
| 迁移 Windows 系统目录 | 不可能 |
| 迁移 `ProgramData` 整体 | 大量软件硬编码，且涉及服务账户权限 |
| 迁移用户 profile 整体 | 支持，但风险极高且 Windows 有官方机制（不在本工具范围） |
| 迁移 OneDrive 接管的目录 | 会破坏同步 |
| 迁移页面文件到网络盘/外置盘 | 会导致严重性能问题甚至系统不稳定 |
| 自动迁移 Tencent 等 IM 数据 | 必须用软件内置功能，工具只提示位置与大小 |
| 自动迁移正在被进程占用的目录 | 无法保证一致性快照 |

## 9. 测试策略

| 测试 | 要求 |
| --- | --- |
| Junction 创建/识别 | 在 `t.TempDir()` 建 Junction，断言：tag 正确、遍历不递归、`SHGetKnownFolderPath` 类调用能穿透 |
| **删除链接不删目标** | 建 Junction → 删链接 → **断言目标目录及内容完好**。这是发布门禁测试 |
| 复制校验 | 造含子目录/空文件/大文件/中文名/长路径的目录树，复制后断言文件数、大小、mtime、ACL 一致 |
| 空间不足 | 用 `VHD` 造一个几乎满的卷，断言预检拒绝且不产生任何副作用 |
| 目标已存在 | 断言预检拒绝，不覆盖 |
| FAT32 目标 | 断言 Junction 机制被拒绝 |
| 环境变量 | 设变量 → 断言注册表已写 → 断言广播被调用（可 mock）→ 断言 `PrevState` 正确记录 |
| 页面文件 | 只测「生成建议」与「journal 记录」，不在测试中真的改系统页面文件 |
| undo | 每个算子执行后 undo，断言系统状态回到执行前的快照（环境变量/注册表可比对；目录内容可比对哈希） |
| 幂等 | 同一 plan 执行两次，第二次应检测到「已迁移」并跳过，不报错不重复搬 |
