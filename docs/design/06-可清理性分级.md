# 06 — 可清理性分级

这是整个工具**最核心、最容易做错**的部分。做错的后果是用户丢数据。因此这篇文档的规则是硬约束，实现时不得为了方便而放宽。

---

## 1. 为什么不用「白名单 / 黑名单」

二元模型的诱惑在于简单，但它会迫使我们在大量灰区上做一个**危险的非黑即白简化**：

| 灰区案例 | 二元模型会怎么判 | 问题 |
| --- | --- | --- |
| `Downloads` 目录 | 白 → 删（用户下载的合同没了）/ 黑 → 不删（但它往往几个 GB） | 正确答案是「列出来，让用户自己勾」 |
| `Windows\Prefetch` | 白 → 删（微软明确不建议，会短暂降低启动速度） | 应是「可以删但有代价」 |
| `.m2` / `npm cache` | 白 → 删（下次构建全部重下，可能几百 MB 流量与十分钟） | 应是「能删，但更好的是迁移」 |
| 微信 `WeChat Files` | 白 → 删（**用户聊天记录和接收的文件全丢**） | 必须是「用户数据，默认不勾」 |
| 浏览器 `Cache` vs `Cookies` | 都在 `User Data` 下，二元模型无法区分 | **必须区分，一个 L2 一个 L0** |
| `C:\Windows\Installer` | 很多「优化教程」说可删 | **删了以后软件无法卸载/修复**，必须永久禁删 |
| 休眠文件 | 是文件不是垃圾 | 应提供「关闭休眠功能」而非「删除文件」 |

所以采用**四级模型**，把「有多危险」和「需要多少人工介入」编码进等级本身。

---

## 2. 四级模型

| 等级 | 名称 | 含义 | 默认勾选 | 是否可被用户强制 |
| --- | --- | --- | --- | --- |
| **L0** | `NEVER` 绝对禁止 | 删除会导致系统/软件损坏或不可逆数据丢失 | 否 | **否**（硬阻断，规则库与 flag 都不能覆盖） |
| **L1** | `CONFIRM` 需确认 | 有风险、影响体验、或属于用户数据 | 否 | 是（须显式 `--include-l1` 且逐项确认） |
| **L2** | `SAFE` 可安全清理 | 可重建、无副作用或副作用极小 | **是** | 是 |
| **L3** | `INFO` 仅报告 | 非垃圾但占空间，只做归因展示 | 否 | 是（仅作为报告，不产生删除动作） |

**默认勾选只有 L2**——这是「扫完直接回车」时的行为，必须百分之百安全。

### 2.1 各等级的补充语义

**L0 的三个子类**（便于报告措辞）：
- `L0-System`：系统关键（`System32`、`WinSxS`、`Installer`）
- `L0-Credential`：凭据/密钥（浏览器 `Login Data`、SSH key、证书）
- `L0-UserGenerated`：用户创作内容（文档、照片、代码仓库）

**L1 的两个子类**：
- `L1-UserData`：用户数据（聊天记录、下载文件、游戏存档）
- `L1-Effort`：可删但有代价（包管理器缓存、Prefetch、更新缓存需停服务）

**L3 的用途**：大文件、虚拟机磁盘、游戏安装目录、未识别目录。它们不该被删，但用户有权知道它们占了空间，且其中一部分**应该被迁移**。

## 3. 判定流程

判定是**优先级链**，先命中者胜出，后续步骤不再执行。这个顺序是安全性的保证。

```
┌─────────────────────────────────────────────────────────────────────┐
│ 步骤 0：路径规范化与合法性校验                                        │
│   - 展开变量 → Clean → 转绝对路径 → 加 \\?\ 校验                      │
│   - 若规范化后路径含 .. 逃逸、或不是绝对路径 → 直接 L0 + 告警           │
│   - 若是 reparse point → 不对链接本身定级，转去评估其目标（见 §3.3）      │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 步骤 1：L0 硬阻断检查（最高优先级，不可覆盖）                           │
│   命中 protected.yaml 中任一规则 → L0，流程结束                        │
│   包含：前缀匹配、精确匹配、正则模式、属性匹配（系统/隐藏/只读+系统）      │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 步骤 2：规则库精准匹配                                                │
│   命中 AppRule.paths[].cleanable_level → 采用声明的等级                │
│   这是「知识」生效的地方（Chrome Cache=L2, Login Data=L0）              │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 步骤 3：系统路径基线匹配（baseline.go）                               │
│   内置一张「Windows 标准路径 → 等级」表（§5），覆盖所有机器都有的路径    │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 步骤 4：启发式定级（置信度门控，见 05 §7.3）                           │
│   conf >= 0.9 且父目录是已知软件数据目录 → L2                          │
│   conf >= 0.7                          → L1                          │
│   conf <  0.7                          → L3                          │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 步骤 5：默认兜底                                                      │
│   路径在系统盘 + 属于某个已识别 App + 未匹配任何规则 → L1               │
│   其余 → L3                                                          │
│   ★ 绝不在未匹配时给 L2 ★                                             │
└─────────────────────────────────────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 步骤 6：后置过滤（不改变等级，只影响「当前是否可操作」）                   │
│   - 年龄过滤：mtime 在 N 天内的 → 标记 TooRecent，本轮跳过              │
│   - 占用过滤：文件被独占打开的 → 标记 InUse，本轮跳过                    │
│   - 路径在其他卷：不在本次扫描范围 → 标记 OutOfScope                    │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.1 为什么 L0 检查必须在规则库之前

因为规则库是**可被用户扩展**的（用户能加自己的规则目录），而 L0 必须是**不可绕过**的。如果先查规则库，一个写错的用户规则就可能把 `C:\Windows\System32` 标成 L2。顺序本身就是安全机制。

### 3.2 为什么「未匹配一律不给 L2」

这是「不知道 → 不删」原则的落地。一个未识别的目录，我们不知道它是缓存还是用户三年的工作成果。默认 L1 或 L3，让用户知情。

### 3.3 reparse point 的定级

链接本身没有空间占用，不能作为清理目标。处理方式：

```
若 path 是 Junction/Symlink:
    不为其本身生成 Finding（占用为 0）
    报告里单独列出：「<path> → <target>（目录联接，未展开）」
    若 target 在扫描范围内，target 会被独立扫描与定级
    若 target 在其他卷，标注「链接目标在 D 盘，本次未扫描」
```

**绝不**对链接本身生成删除动作——否则「删除这个零字节链接」看起来无害，实际可能诱导用户或后续算子在链接上做递归删除。

## 4. L0 硬阻断清单（protected.yaml 的内容概览）

完整表在规则库里，这里列出**必须覆盖**的类别。这份清单的正确性由**代码评审 + 危险用例测试**双重保证（见 `09`）。

### 4.1 系统关键目录

| 路径 | 理由 |
| --- | --- |
| `%SystemRoot%` 本身、`System32`、`SysWOW64` | 操作系统核心 |
| `%SystemRoot%\WinSxS` | 组件存储。删除会导致系统无法更新/修复。正确做法是 `DISM /StartComponentCleanup`，不是手删 |
| `%SystemRoot%\Installer` | **MSI 缓存**。删除后已安装软件无法卸载、无法修复、无法更新。**这是最常被"优化教程"误导误删的目录** |
| `%SystemRoot%\Fonts` | 字体 |
| `%SystemRoot%\Boot`、`Boot\EFI`、`bootmgr`、`BCD` | 引导 |
| `%SystemRoot%\System32\config` | 注册表 hive |
| `%SystemRoot%\System32\drivers` | 驱动 |
| `%SystemRoot%\assembly` | .NET GAC |
| `%SystemRoot%\servicing`、`%SystemRoot%\CBS` | 服务栈 |
| `%SystemRoot%\security` | 安全数据库 |
| `%SystemRoot%\System32\LogFiles` | 部分含安全审计（谨慎，整体归 L0） |
| `C:\Recovery`、`C:\Boot` | 恢复环境 |
| `C:\System Volume Information` | 卷影副本/还原点 |
| EFI 系统分区、恢复分区、保留分区 | 无盘符，但若被挂载必须阻止 |

### 4.2 页面/休眠文件与系统级文件

| 路径 | 理由 |
| --- | --- |
| `pagefile.sys` | 虚拟内存。不能删（应通过系统设置调整） |
| `swapfile.sys` | UWP 交换文件 |
| `hiberfil.sys` | 休眠映像。**不能直接删**；应提供 `powercfg /h off`（属于「功能关闭」而非「删除」） |
| `DumpStack.log.tmp` | 内核 |
| `MEMORY.DMP`（在 `%SystemRoot%` 下） | 完整内存转储，**可以删**但体积可能是内存大小（16–64 GB）→ 归 L1「可删但有诊断价值」 |

### 4.3 已安装程序本体

| 路径 | 理由 |
| --- | --- |
| `%ProgramFiles%\*`、`%ProgramFiles(x86)%\*` 下的**已安装软件目录** | 删除会破坏软件。**但**：若该目录经判定为「已卸载残留」（`Orphaned`），降级为 L1 |
| `%ProgramData%\Microsoft\Windows\Start Menu` | 开始菜单 |
| `%ProgramData%\Microsoft\Windows\SystemData` | 系统 |
| `%LOCALAPPDATA%\Microsoft\Windows\WinX` | Win+X 菜单 |
| `%LOCALAPPDATA%\Packages\*` | UWP 应用数据（见 §6.5） |
| `%ProgramFiles%\WindowsApps` | Store 应用安装位置，受 ACL 保护 |

### 4.4 凭据与密钥（L0-Credential）

| 路径 | 理由 |
| --- | --- |
| 浏览器 `Login Data`、`Login Data For Account`、`Web Data`（自动填充） | 保存的密码 |
| 浏览器 `Cookies`、`Network\Cookies` | 登录态（删了要重新登录所有网站） |
| 浏览器 `Bookmarks`、`Bookmarks.bak` | 书签 |
| 浏览器 `History` | 浏览历史（用户可能要看） |
| 浏览器 `Preferences`、`Secure Preferences` | 配置（含已保存的凭据相关设置） |
| 浏览器 `Local State` | 含加密密钥引用 |
| `%APPDATA%\Microsoft\Crypto`、`%APPDATA%\Microsoft\Protect` | DPAPI 密钥 |
| `%APPDATA%\Microsoft\SystemCertificates`、`%APPDATA%\Microsoft\Certificates` | 证书 |
| `%USERPROFILE%\.ssh`、`%USERPROFILE%\.gnupg`、`%USERPROFILE%\.aws`、`%USERPROFILE%\.kube`、`%USERPROFILE%\.docker\config.json` | 各类凭据 |
| `%APPDATA%\Code\User\settings.json`、`keybindings.json`、`snippets` | 编辑器配置（用户心血） |
| 任何 `*.pfx`、`*.p12`、`*.pem`、`*.key`、`*.keystore`、`*.jks` | 证书与私钥 |
| 任何 `id_rsa`、`id_ed25519`、`known_hosts`、`authorized_keys` | SSH |
| `%APPDATA%\Microsoft\Credentials`、`%LOCALAPPDATA%\Microsoft\Credentials` | 凭据保管库 |

### 4.5 用户生成内容（L0-UserGenerated）

| 路径 | 理由 |
| --- | --- |
| `Documents`（重定向后也要用实际路径判定） | 用户文档 |
| `Desktop`、`Pictures`、`Videos`、`Music` | 同上 |
| **任何代码仓库目录**（含 `.git`） | 未提交的工作 |
| 任何含 `.git`、`.svn`、`.hg` 的目录 | 同上 |
| Office 文档 `*.docx/xlsx/pptx/pdf` 所在的非缓存目录 | |
| 设计/媒体工程文件 `*.psd/ai/sketch/fig/blend/prproj` | |
| 数据库文件 `*.db/sqlite/mdf/accdb`（非缓存类） | |
| 虚拟机磁盘 `*.vhd/vhdx/vmdk/qcow2` | 用户数据，归 L3（大文件）+ 可迁移 |

### 4.6 允许清单的对称性检查

实现时必须写一个测试：**对 L0 清单里每个路径，断言 `Grade(path) == L0`**，且断言**任何 L0 路径的后代也至少是 L0**（除非被显式豁免）。这个测试叫 `TestProtectedPathsNeverDeletable`，是发布前的门禁。

## 6. 灰区案例与决策

这是这篇文档最重要的部分——**每个灰区都要有一个明确、可辩护的决策**。

### 6.1 `Downloads` 目录

**决策：L1，且必须逐项展示（不按目录整体勾选）。**

理由：这个目录里可能同时有「三年前下载的安装包」（可删）和「客户发来的合同 PDF」（绝不能删）。工具没有能力判断内容价值，所以**只做展示与排序，把选择权交给用户**。

具体做法：
- 按文件大小降序列出（大文件优先，用户最想清）
- 提供辅助信号：**安装包类**（`*.exe`、`*.msi`、`*.zip` 且 mtime > 90 天）可以建议删除，但**仍需用户勾选**
- 明确排除 `*.doc*`、`*.xls*`、`*.pdf`、`*.jpg` 等文档类型，不给删除建议（只展示大小）

### 6.2 浏览器：`Cache` vs 用户数据

**决策：`Cache` / `Code Cache` / `GPUCache` / `ShaderCache` / `CacheStorage` = L2；`Cookies` / `Login Data` / `Bookmarks` / `History` / `Preferences` / `Local State` = L0。**

这是本工具「精细度」的核心体现。实现要求：
- 规则库必须对 Chromium 系（Chrome、Edge、Brave、零信浏览器、Electron 应用）逐个声明子路径等级
- **禁止**用「目录名含 `Cache` 就 L2」这类全局规则吃遍所有软件——Electron 应用里 `Cache` 目录位置各不相同，必须靠规则库精确声明 + 通配 profile
- `Service Worker\CacheStorage` = L2（纯缓存），但 `Service Worker\ScriptCache` 与注册信息 = L1（删除会导致离线应用失效）

> 本机实测提醒：`%LOCALAPPDATA%\Google\Chrome\User Data\Default\Cache` 是 0 MB（Chrome 新版把缓存移到了 `Cache\Cache_Data`），而 Edge 的 `Cache` 是 222 MB。**规则库必须同时声明新旧两种布局**，否则查不到现代 Chrome 的缓存。

### 6.3 `C:\Windows\Installer`

**决策：L0，永久禁删。且规则库里要写清理由，防止后人"优化"掉这条。**

这是被"系统优化教程"祸害最严重的目录。它存放 MSI 安装包缓存，`.msi` + `.msp`。删除后果：
- 已安装的 MSI 软件**无法卸载**
- **无法修复**（`修复` 按钮会失败）
- **无法更新**（更新需要原始 MSI）
- **无法更改安装选项**（增删组件）

正确做法：只报大小（常达 2–5 GB），提示「这是 MSI 缓存，删除会导致软件无法卸载/修复/更新。如需释放，请卸载不用的软件」。提供**永不删除的硬保证**。

### 6.4 包管理器缓存（`.m2`、npm、pip、Gradle、Go、Cargo）

**决策：L1（可删但有代价），且迁移优先级高于删除。**

理由：删掉后下次构建需要重新下载（`.m2` 3 GB 可能对应几十分钟的网络时间），这对开发者是**真实的成本**。而且这些缓存的正确出路是**搬到 D 盘**，不是删除。

对本机的具体建议：

| 缓存 | 大小 | 删除代价 | 推荐动作 |
| --- | --- | --- | --- |
| `.m2\repository` | 3.0 GB | 重新下载所有依赖 | **迁移**（改 Maven `settings.xml` 的 `localRepository`） |
| `.cache\puppeteer` | 2.7 GB | 重新下载 Chromium（约 150 MB × 版本数） | **迁移**（`PUPPETEER_CACHE_DIR`）或删除（若不再用） |
| `.cache\codex-runtimes` | 0.78 GB | 重新下载运行时 | 迁移（`--cache-dir` 或对应环境变量） |
| pip `Cache` | 0.31 GB | 重新下载 wheel | 迁移（`PIP_CACHE_DIR`） |
| npm-cache | 0.30 + 1.0 GB | 重新下载包 | 迁移（`NPM_CONFIG_CACHE`） |

**重要**：优先建议用工具**自身的清理命令**而非直接删目录：
- `npm cache clean --force` 而不是删 `_cacache`
- `pip cache purge` 而不是删 `Cache`
- `mvn dependency:purge-local-repository`、`go clean -modcache`、`gradle --stop && 删 caches`

原因：这些工具有自己的元数据一致性要求，暴力删目录可能留下不一致状态。**设计含义**：`plan.json` 的算子类型里要支持 `RunCommand` 算子（不只是 `DeleteDir`）。

### 6.5 UWP / Store 应用数据

`%LOCALAPPDATA%\Packages\<PackageFamilyName>\` 下的子目录等级：

| 子目录 | 等级 | 理由 |
| --- | --- | --- |
| `LocalCache\` | L2 | UWP 约定的缓存位置 |
| `TempState\` | L2 | 临时状态 |
| `AC\` | L1 | 应用容器内部数据，可能是用户数据 |
| `LocalState\` | **L0** | **应用数据主体**（如邮件、笔记、游戏存档） |
| `RoamingState\` | **L0** | 同上 |
| `Settings\` | **L0** | 应用设置 |
| `SystemAppData\` | **L0** | 系统 |

**坑**：`Packages` 下的目录名含 `!` 和哈希（如 `Microsoft.WindowsCalculator_8wekyb3d8bbwe`），且**部分目录是 reparse point**（Store 应用的"写入重定向"机制）。遍历时必须识别，否则会陷入循环或重复计数。

### 6.6 休眠文件

**决策：L1，且以「关闭休眠功能」的形式呈现，不做文件删除。**

```
提示：hiberfil.sys 占用 6.4 GB（约等于内存大小的 40%）
      这是休眠/快速启动的映像文件，不能直接删除。
      可通过 `powercfg /h off` 关闭休眠功能释放空间。
      副作用：失去休眠与快速启动能力。
      [需要管理员权限]
```

**设计含义**：算子类型需要 `ChangeSystemSetting`，且必须是**可逆的**（`powercfg /h on` 恢复），并且要在 journal 里记录以便回滚。

### 6.7 卸载残留（Orphaned）

**决策：L1。**

场景：注册表有卸载记录但安装目录不存在（本机 67% 条目缺 `InstallLocation`，反推失败会大量产生这种情况）。要区分：

| 情况 | 判定 | 措辞 |
| --- | --- | --- |
| 反推出路径 + 路径不存在 + 该软件在别的路径找到 | 反推失败，不是残留 | 报告「识别不完整」，归 L3 |
| 反推出路径 + 路径不存在 + 别处也没有 | 疑似卸载残留 | L1「疑似卸载残留，占 X MB」 |
| 注册表记录存在但没有反推出任何路径 | 信息不足 | L3，不形成删除建议 |

**绝不允许**：仅因为「注册表里有条记录指向不存在的路径」就自动建议删除整个父目录。必须限定在**明确的软件专属目录**（如 `%LOCALAPPDATA%\<确切名字>`）且该目录下**没有**其他软件的痕迹。

### 6.8 其他需要明确决策的灰区

| 项 | 决策 | 理由 |
| --- | --- | --- |
| `Windows.old` | L1 | 升级备份，可回滚到旧版本。10 天后 Windows 自动删。存量大（10–30 GB） |
| `Prefetch` | L1 | 见 §5.2 |
| `NTUSER.DAT.LOG*`、`*.regtrans-ms` | L0 | 注册表事务日志 |
| `%SystemRoot%\System32\winevt\Logs` | L0 | 事件日志，含安全审计 |
| `%ProgramData%\Microsoft\Windows Defender` | L0 | 杀软定义与隔离区 |
| 杀软/安全软件的任何目录 | L0 | category=security 的软件整体 L0 |
| `.git` 目录（即使很大） | L0 | 版本历史 |
| `node_modules` | L3 | 可重建但重建代价大（网络+时间），且是**项目的一部分**。只报大小，绝不建议删 |
| `__pycache__`、`*.pyc` | L2 | 纯派生 |
| `target`（Rust/Cargo）、`build`、`dist`、`out` | L3 | 构建产物，可重建但可能含交付物。只报 |
| `.gradle\caches` | L1 | 同 §6.4 |
| 微信 `WeChat Files` / `%APPDATA%\Tencent` | L1 | **用户数据**，必须用微信自带的「存储空间管理」或「文件管理」迁移，工具只指出位置与大小 |
| `%APPDATA%\secoresdk`（本机 0.86 GB，未识别） | L3 | 未识别 → 只报告 |
| Docker `ext4.vhdx` | L3 + 迁移建议 | 巨大且是用户数据。可迁移（Docker Desktop 设置）；**且可用 `docker system prune` 收缩内部空间** |
| WSL2 发行版 `ext4.vhdx` | L3 + 迁移建议 | 同上，`wsl --export/--import` 迁移 |

## 7. 后置过滤（步骤 6）

等级与「当前能不能操作」是两件事。

### 7.1 年龄过滤

| 路径类型 | 最小年龄 |
| --- | --- |
| 临时文件（`Temp`、`tmp`） | 24 小时（**必须**，否则可能删掉正在写入的文件） |
| 崩溃转储、日志 | 7 天 |
| 浏览器缓存 | 0（缓存被占用时会失败，靠占用检测兜底） |
| 更新缓存 | 0（但需停服务） |

`mtime > 阈值` 才可操作，否则标记 `TooRecent` 并在报告中说明「X 个文件因近期修改被跳过」。

### 7.2 占用检测

删除前（以及**扫描时**做预判）：

```go
// 尝试以独占方式打开；失败说明有进程在用
f, err := os.OpenFile(path, os.O_RDWR, 0)
// 或用 CreateFileW 带 0 共享模式
h, err := winapi.CreateFileW(path, GENERIC_READ, 0 /*no sharing*/, ...)
if err == ERROR_SHARING_VIOLATION {
    // 被占用 → InUse
}
```

**注意**：有些进程用 `FILE_SHARE_DELETE` 打开文件，此时删除会成功但进程行为异常。所以除了共享冲突，还要检查是否有进程持有句柄（`NtQuerySystemInformation` 或 `RestartManager` API 枚举句柄持有者）。初期实现用共享冲突检测够用，后续用 Restart Manager 增强。

**DirInUse 的传播**：若目录下任意文件被占用，则整个目录标记为 `InUse`（部分可删会造成软件状态不一致）。

### 7.3 报告必须体现过滤结果

```
可安全清理（L2）合计 1.4 GB
  其中本轮可操作 1.1 GB
  跳过 0.3 GB：281 MB 被占用 / 19 MB 修改时间 < 24h
```

## 8. 可解释性要求（FR-31）

每一个 Finding **必须**携带可读理由。理由不是日志，是**给用户看的**。要求：

| 字段 | 要求 |
| --- | --- |
| `Level` | L0–L3 |
| `Reason` | 一句中文，说清「为什么是这个等级」 |
| `MatchRule` | 命中的规则 ID（如 `google.chrome.paths[1]`）或 `baseline:temp-user` 或 `heuristic:cache` |
| `Confidence` | 0.0–1.0，启发式的置信度；规则命中的为 1.0 |
| `Consequence` | 「删了会怎样」——L1/L2 必须写 |
| `Recommendation` | 「更好的做法」——如「建议迁移而非删除」 |

示例输出：

```
┌─ L2 可安全清理 ────────────────────────────────────────────────────────┐
│ 304 MB  C:\Users\33380\AppData\Local\npm-cache                        │
│   类型：包管理器缓存 (npm)                                              │
│   归属：npm (runtime)                                                 │
│   理由：npm 下载的包缓存，删除后下次安装会重新下载（需联网）                │
│   依据：rule:npm.cache@1.0  (置信度 1.0)                                │
│   后果：下次 npm install 变慢，无功能损失                                 │
│   建议：★ 更好的做法是迁移到 D 盘并设置 NPM_CONFIG_CACHE，而非删除         │
└───────────────────────────────────────────────────────────────────────┘

┌─ L0 绝对禁止 ──────────────────────────────────────────────────────────┐
│ 1.2 GB  C:\Users\33380\AppData\Local\Google\Chrome\User Data          │
│   类型：用户数据（配置、书签、Cookie、历史）                              │
│   归属：Google Chrome (browser)                                        │
│   理由：包含书签、保存的密码、登录状态。删除会导致密码与书签永久丢失         │
│   依据：rule:google.chrome.paths[0]  (置信度 1.0)                       │
│   ★ 其中 222 MB 为缓存部分（可安全清理），将在 L2 分组中单独列出            │
└───────────────────────────────────────────────────────────────────────┘
```

最后那条 note（「其下有可清理的子项」）很重要——它让用户理解**为什么一个大目录被判 L0，但依然有清理空间**，避免用户觉得工具无能而去找野路子工具。

## 9. 测试策略（安全关键）

| 测试 | 要求 |
| --- | --- |
| `TestProtectedPathsNeverDeletable` | L0 清单中**每一条**路径及其**所有后代**都必须是 L0。发布门禁 |
| `TestNoUnmatchedIsL2` | 随机生成/从真实数据采样的未匹配路径，断言等级 ≠ L2 |
| `TestBrowserCacheVsCredential` | Chromium 全家族：`Cache` 系列 = L2，`Login Data`/`Cookies`/`Bookmarks` = L0 |
| `TestHeuristicConfidenceGating` | 置信度 0.85 的启发式结果必须是 L1 而非 L2 |
| `TestReparseNeverGraded` | 对 Junction/Symlink 断言不产生删除动作 |
| `TestUserDataNeverL2` | 对 `Documents`/`Desktop`/`Pictures`/`Videos`/`Music`（含重定向后的实际路径）、任何含 `.git` 的目录，断言 ≠ L2 |
| `TestKnownFolderRedirect` | Known Folder 被重定向后，判定必须用实际路径（不能漏判新的 Documents 位置） |
| `TestOneDriveTakeover` | OneDrive 接管的目录不参与迁移，且被标注 |
| `TestChinesePaths` | 含中文的路径（`图片`、`微信`、`文档`、`飞书`）全程正确 |
| Fixture 回归 | 把本机真实扫描结果存为 fixture，每次改规则后跑一遍，**对比等级变化**——任何等级从 L0/L1 降到 L2 的变更都必须人工 review |
