# 14 — 主副页面与 AI 集成设计

> 状态：已实现(第一版) · 2026-09-14
> 需求原话：主页面是 AI 大模型的对话框,有大模型就能聊天并提供功能入口;
> 完全不用大模型时这块不加载,选其他功能当默认主页;两种模式可来回切换。

---

## 1. 核心模型：主功能 1 个 + 扩展功能 N 个，主页即配置

```
                    ┌──────────────────────────────┐
                    │  config.yaml                  │
                    │  general.home: chat | scan…   │ ← 主功能 = 启动时显示谁（恰好一个）
                    │  modules.<id>.enabled: bool   │ ← 每个扩展页的可见开关
                    │  ai.{provider,base_url,…}     │ ← 决定聊天是否真正可用
                    └──────────────┬───────────────┘
                                   │
        ┌──────────────────────────▼───────────────────────────┐
        │  左侧导航栏                                            │
        │  [主功能页]  ← general.home 指向的页面，启动即显示        │
        │  ──────────                                           │
        │  🔍 磁盘扫描  ┐                                        │
        │  🧹 垃圾清理  ├ 扩展功能页（N 个，来自模块注册表）           │
        │  📦 空间迁移  ┘ 禁用的不出现在导航，后端也绝不初始化          │
        │  ⚙ 设置                                              │
        └──────────────────────────┬───────────────────────────┘
                                   │ 前端页面切换（毫秒级，页面状态保留）
     ┌─────────────┬───────────────┼───────────────┬─────────────┐
     ▼             ▼               ▼               ▼             ▼
  聊天页        扫描页           清理页           迁移页         设置页
 (AI未配置→    (已有)          (开发中,         (规划中)      (主页选择/
  引导配置)                     不可进入)                       AI配置/模块开关)
```

**主功能与扩展功能的关系（用户口径：副功能支持多个，就是扩展功能页面）**：

| | 主功能页面 | 扩展功能页面 |
| --- | --- | --- |
| 数量 | **恰好 1 个** | **N 个**（随模块注册增长） |
| 由谁决定 | `general.home` 配置指向某个模块 id | 模块注册表 + 各自的 enabled 开关 |
| 启动时 | 直接渲染它 | 不渲染，仅在导航中占位（禁用的不占位） |
| 可以是谁 | 任何已启用模块（聊天/扫描/未来的清理） | 任何注册模块 |
| 切换 | 左侧导航随时点，**页面状态保留**（聊天记录、扫描结果不丢） | 同左 |

**新增一个扩展页 = 注册一个 Module + 加一个前端页面，框架零改动。**
主/副的区分只是「`general.home` 指向谁」——聊天和扫描在架构上完全平等，
所以「AI 主页模式」与「工具主页模式」不是两套代码，只是配置值不同。

**三条不变式**：

1. **主页是配置，不是写死**。`general.home` 指向任何存在的页面 id；启动时直接渲染它。
2. **导航按配置过滤**。`modules.<id>.enabled = false` 的页面不出现在导航里，
   后端也绝不初始化——AI 模块禁用时，聊天相关代码零执行、零网络请求。
3. **切换是显示/隐藏，不是销毁重建**。从聊天切到扫描再切回来，聊天记录与扫描结果都还在；
   每个页面自身的重活（扫描、网络请求）仍然只由用户显式触发。

## 2. AI 模块的三态（诚实的加载语义）

| 状态 | 判定 | 行为 |
| --- | --- | --- |
| **未配置** | `ai.base_url` 或 `ai.api_key` 为空 | 聊天页显示配置引导；**不发起任何网络请求**，不加载任何 SDK/连接 |
| **已配置** | base_url + api_key + model 齐全 | 可聊天；首次发送才建立 HTTP 连接（OpenAI 兼容 `/chat/completions` 流式） |
| **模块禁用** | `modules.chat.enabled = false` | 导航不出现聊天页；主页若指向 chat 则自动回退到 scan 并提示 |

API Key **明文存在本机配置文件**（`%APPDATA%\winclean\config.yaml`）。界面与文档都明确提示这一点。
不上传任何数据；聊天请求只发往用户自己填写的 base_url。

## 3. 聊天调用功能的两层设计

### L1 快捷工具卡（本期实现，确定性）

聊天输入框上方常驻功能 chips（「扫描 C 盘」「查看最大文件」…），点击直接调用本地模块，
结果以卡片形式插入对话流。**不依赖模型、不需要 API Key、不联网**——
即使 AI 完全没配置，这些入口也能用，AI 只负责「对话」这一层。

### L2 模型驱动的 Function Calling（规划，M-AI2）

```
用户消息 → 组装 tools schema（每个已启用模块暴露 tool 定义）
        → 发给模型（带 tools）
        → 模型返回 tool_calls？
             ├─ 是 → 本地执行对应模块动作 → 结果回填为 tool 消息 → 再次请求
             └─ 否 → 直接展示回答
```

- 工具注册表与 `modules.Registry` 同源：模块声明自己暴露哪些 tool（名称、参数 schema、执行函数），
  没启用的模块其 tool 不进入请求——**模型能调用的功能 ⊆ 用户启用的功能**。
- 执行前按危险等级确认：只读工具（扫描/查询）直接执行；写操作（清理/迁移）必须回传确认卡片，
  用户点确认才执行。这条与 `06` 可清理性分级的「默认只勾 L2」一脉相承。
- 依赖支持 tools 的模型；不支持时自动降级为 L1（提示用户用快捷卡）。

## 4. 为什么这样切是「流畅」的

- 导航切换只改 `display`，无路由库、无页面重载；扫描页离开时扫描继续在后台跑（进度轮询不中断）。
- 每页重活都由用户动作触发；页面常驻让「扫完切去聊天问一句，再切回来看结果」成为自然动线。
- 启动只做：读配置 → 建模块注册表（元数据） → 渲染主页。启动耗时显示在标题旁（`启动 X ms`），
  以后任何功能如果拖慢它，一眼可见。
