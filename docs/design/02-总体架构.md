## 2. 模块职责

| 模块 | 职责 | 明确不做什么 |
| --- | --- | --- |
| `cmd/winclean` | 命令定义、参数校验、调用用例、格式化输出 | 不含业务逻辑 |
| `internal/app` | 编排扫描 → 分析 → 报告的流程；进度上报；错误聚合 | 不做判定，不碰 syscall |
| `internal/scan` | 只产出**事实**：有哪些文件、多大、什么时候改的 | 不判断「能不能删」（那是 cleanability 的事） |
| `internal/analyze/inventory` | 产出「装了哪些软件」 | 不统计空间 |
| `internal/analyze/attribution` | 把扫描到的事实变成「空间被谁占了」 | 不做安全判断 |
| `internal/analyze/cleanability` | 给每个 Finding 定级 L0–L3 + 理由 | 不执行删除 |
| `internal/analyze/migratability` | 判定可迁移项、选择机制、生成迁移计划 | 不执行迁移 |
| `internal/analyze/rules` | 规则库加载、变量展开、模式匹配、优先级裁决、硬阻断 | 不含具体软件知识（知识在 YAML 里） |
| `internal/sys` | Windows 系统事实的唯一入口，屏蔽 syscall 细节 | 不含业务判断 |
| `internal/winapi` | 纯 syscall 封装 | 无任何业务逻辑，100% 可单测 |
| `internal/model` | 数据模型定义 | 无依赖、无方法（或只有纯函数方法） |
| `internal/catalog` | 规则库的加载与校验 | 不负责匹配（匹配在 rules 中） |
| `internal/report` | 渲染输出 | 不做计算 |

```
            ┌────────────────┐          ┌────────────────────┐

            ┌────────────────────┐        ┌──────────────────────┐
            │ plan migrate        │───────►│ plan.json（变更计划）  │

            └────────────────────┘        └──────────────────────┘
```

**关键约束**：`scan.json` 是**唯一的事实来源**。`report`、`plan`、`app`、`paths` 等命令一律读 `scan.json`，绝不重新扫描。这保证了：

- 同一份数据上可以反复试不同的判定规则（开发规则库时的核心效率来源）
- 报告与计划可复现、可 diff
- 扫描（慢）与判定（快）解耦

## 4. 并发模型

扫描是 IO 密集型，瓶颈在目录枚举与元数据读取。

```
main goroutine
  │
  ├─ 卷级并行：每个盘一个 coordinator（通常 1 个，C 盘为主）
  │
  ├─ 目录级并行：worker pool，默认 runtime.NumCPU()*2，上限 32
  │     每个 worker 从 workQueue chan *DirTask 取任务
  │     用 FILE_FLAG_OPEN_REPARSE_POINT 读目录项，逐个判断
  │
  ├─ 流式聚合：worker 不做全局聚合，只把 DirStat 发到 aggChan
  │     aggregator goroutine 单线程维护目录树聚合（避免加锁）
  │     父目录统计通过「自底向上完成后回传」而非「累加」实现
  │
  └─ 背压：workQueue 有界（默认 4096），满了 worker 阻塞 → 自然限流
```

**为什么单线程聚合**：多线程累加同一棵树的计数需要细粒度锁，反而更慢且易错。单聚合 goroutine 处理的是纯粹的数值运算，不会是瓶颈（瓶颈在 syscall）。

**内存控制**（NFR-2 要求 ≤ 300 MB）：
- 只保留「需要上报的目录节点」：深度 ≤ `--max-depth` 的节点，以及所有命中规则/命名模式的节点
- 中间层目录只保留聚合数值不留 `DirNode` 对象
- 大目录（如 `node_modules`）内部用固定大小的统计结构，不逐文件建对象
- 单目录文件数超过阈值（默认 200k）时，只统计总量不再细分

**取消与超时**：所有 worker 共享 `context.Context`；Ctrl+C 触发 cancel，worker 检查点立即返回，aggregator 收尾后输出已完成部分（FR-5）。

## 7. 错误处理与日志

| 场景 | 策略 |
| --- | --- |
| 单目录无权限（`ERROR_ACCESS_DENIED`） | **不中断**。记录到 `ScanStats.Skipped`，报告末尾汇总「N 个目录因权限跳过，建议以管理员运行以获取完整结果」 |
| 单文件读取失败 | 跳过，计入 `ScanStats.Errors`，debug 日志记录 |
| 注册表键不存在 | 正常情况（如无 WOW6432Node），静默跳过 |
| 规则库解析失败 | **启动即失败**（fail fast）。规则库是内置资源，解析失败是构建缺陷 |
| 规则匹配不到任何 App | 不报错，记为 `unknown` 走归因 |
| 路径模板展开后不存在 | 不报错，标记 `Exists=false`，不参与后续判定 |
| 磁盘在扫描中卸载 | 记录并跳过该卷 |
| 用户 Ctrl+C | 优雅退出，输出已完成部分，退出码 130 |

日志用 `log/slog`，默认 `WARN`，`--verbose` 提升到 `DEBUG`，`--quiet` 降到 `ERROR`。日志写 stderr，结果写 stdout——保证 `winclean scan --format json > scan.json` 可直接管道使用。

## 8. 配置

三层，后者覆盖前者：

1. **内置默认**（代码常量 + 规则库）
2. **用户配置文件** `%APPDATA%\winclean\config.yaml`：默认排除路径、自定义规则库目录、并发数、缓存位置
3. **命令行 flag**（最高优先级）

配置文件示例：

```yaml
scan:
  workers: 8
  max_depth: 4
  min_size: 10485760        # 只上报 ≥10MB 的目录，避免报告被小条目淹没
  follow_reparse: false     # 危险开关，默认关闭，不建议打开
  exclude:
    - "C:\\Windows\\WinSxS"
    - "C:\\$Recycle.Bin"
rules:
  extra_dirs:
    - "%APPDATA%\\winclean\\rules"   # 用户自定义规则库
  disable:
    - "app.some-rule-id"             # 禁用某条规则（L2 可禁用，L0 不可）
report:
  format: table
  sort_by: size
  group_by: level
```
