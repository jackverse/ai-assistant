# 22 — 对外能力接口与 AI 可控制规范

> 需求：所有功能都必须有 API 接口对外暴露，AI 能轻松控制这个软件。
>
> **先要解决一个矛盾**：本项目的硬规则是「不常驻服务、不驻留后台」
> （见 `20-扩展模块架构规范.md`），而「对外暴露 API」的直觉做法是
> 起一个常驻 HTTP 服务——两者直接冲突。

---

## 1. 矛盾的解法：默认 CLI 形态，HTTP 按需开启

**"对外暴露 API" 不等于"起一个常驻服务"。** 对一个桌面工具，
最合适的对外接口形态取决于调用方：

| 形态 | 常驻 | 适合谁 | 本项目定位 |
| --- | --- | --- | --- |
| **CLI / stdio 的 JSON 接口** | **零常驻** | AI Agent、脚本、CI、你手动调试 | **默认形态** |
| 本机 HTTP 监听 | 常驻 | 需要订阅进度、被外部编排器长连接的场景 | **可选**，`api.enabled: true` 才启动，默认关闭 |

为什么 CLI 是默认：**AI 本来就会执行命令并读 JSON**。
`助手.exe api call scan.start --json '{"disk":"C"}'` 一条命令就是一个 API 调用——
零端口占用、零监听、进程退出即结束，与「把模块代码删掉不影响启动」完全兼容。

HTTP 只在确有必要时开：例如外部编排器要持续接收扫描进度。
开启时**只绑 127.0.0.1**，不对外网暴露。

---

## 2. 统一契约（这是"轻松控制"的关键）

### 2.1 三类动作 + 可发现 + 自描述

```bash
助手.exe api list                      # 列出全部能力（AI 先调这个就知道能做什么）
助手.exe api describe scan.start       # 参数名/类型/是否必填/示例/危险等级
助手.exe api call scan.start --json '{"disk":"C"}'
助手.exe api call report.decision      # 无参数动作
```

`api list` 的输出形如：

```json
{
  "ok": true,
  "data": {
    "actions": [
      {"id":"scan.start","module":"scan","kind":"readonly",
       "summary":"开始扫描磁盘","params":[{"name":"disk","type":"string","required":true,"example":"C"}]},
      {"id":"report.decision","module":"scan","kind":"readonly",
       "summary":"三色决策清单（能删/需确认/不要动）","params":[]}
    ]
  }
}
```

### 2.2 统一响应信封

```json
{ "ok": true,  "data": { ... } }
{ "ok": false, "error": "人类可读的失败原因", "hint": "怎么修" }
{ "ok": false, "error": "该动作会修改系统状态", "need_confirm": true, "hint": "确认后加 --confirm 重试" }
```

`hint` 是硬性要求：**失败必须告诉调用方怎么办**。
AI 拿到 `{ok:false, error}` 没有 hint 就只能干瞪眼——
这与预检清单「未通过项必须带修复建议」是同一条原则。

### 2.3 危险分级

| 级别 | 含义 | 行为 |
| --- | --- | --- |
| `readonly` | 只读，不改任何东西 | 直接执行 |
| `mutating` | 会改状态（写文件、启动进程） | 直接执行，但在响应里回显改了什么 |
| `destructive` | **会删数据** | **默认拒绝**，必须显式 `--confirm` 且动作内部仍走 dry-run 优先 |

`destructive` 的默认拒绝是**代码行为**，不是文档约定——见 §4 的测试。

## 3. 与模块规则的关系

**能力 = 模块**。每个在 `registerModules()` 注册的模块，
**必须至少暴露一个 action**，且 action id 以模块 id 为前缀（`scan.start`、`deploy.pack`）。

这条把两套规则缝合起来：
- 模块规则管「不用的功能不加载」
- 本规则管「加载得到的功能，AI 都能调」

合起来就是：**功能既能按需加载，也能被 AI 发现与驱动。**

---

## 4. 让规则可验证（不是口号）

本项目的风格是「规则必须可证伪」。三条强制测试：

| 测试 | 断言 |
| --- | --- |
| `TestEveryModuleHasAction` | 遍历 `modules.Registry` 里每个已注册模块，api 注册表中必须存在 `module.action` |
| `TestEveryActionIsDescribed` | 每个 action 有 summary；必填参数有 type 与 example；kind 属于三个合法值 |
| `TestDestructiveRequiresConfirm` | 未传 confirm 调用 destructive action 必须返回 `need_confirm: true` 且**没有任何副作用** |

第三条尤其重要：它把「危险动作默认拒绝」从文档承诺变成可断言的代码行为。

---

## 5. 新增能力时必须做的

1. 在 `internal/<id>/` 实现纯逻辑
2. 在 `api_actions.go` 注册 action（含 summary、params、kind）
3. **危险动作**：`kind: destructive`，且 handler 内部先检查 confirm
4. `make test` 通过（三条强制测试会自动检查你的模块）

不允许的写法：
- 只给前端加按钮、不暴露 action —— AI 就控制不了这个功能
- action 直接调用 `wails` 的事件推送（headless 下没有 `ctx`，会 panic）
  → 事件推送只做「有 ctx 才发」的判断（现有代码已如此）
- 开了 HTTP 监听却绑 `0.0.0.0`
