# 16 — 部署模块「配置与运行分离」设计

> 需求：配置和运行要分开；最好是傻瓜式的。
> 状态：已实现（v1.1）

---

## 1. 问题：现在这一页为什么不够傻瓜

当前部署页把四类东西平铺在一屏：

```
工具链（JDK / Maven 下拉）
目录（代码根 / 输出目录 / 保留环境）
项目与模块（下拉 + 勾选 + 导入按钮）
开始打包 + 日志
```

对第一次打开的人，这等于**一上来就要回答 4 个问题**：选哪个 JDK、代码在哪、
产物写哪、要打哪个模块。其中「导入既有配置」还是必备前提——
不导入就一个模块都没有。这不是傻瓜式，这是把配置和运行的责任一起丢给用户。

**根因**：配置（一次性、需要判断）和运行（每次重复、不该需要判断）混在一起。
这两件事的心智负担完全不同，应该分开。

---

## 2. 设计：两个页签，各司其职

部署页内部拆为两个页签：

```
┌─ 部署打包 ────────────────────────────────────────────────┐
│  [ 打包 ]  [ 配置 ]        ← 默认停在「打包」               │
├───────────────────────────────────────────────────────────┤
│  打包页（傻瓜式：只回答"现在能不能打"和"点了会发生什么"）      │
│                                                            │
│   预检清单                                                 │
│     ✓ JDK        17.0.9 (D:\workplace\jdk17)              │
│     ✓ Maven      3.9.6                                     │
│     ✓ 代码根目录   D:\code                                  │
│     ✓ 输出目录     D:\record\product-project\product（可写） │
│     ✓ 模块        2 个后端 + 2 个前端，目录与脚本齐全          │
│                                                            │
│   本次将产出                                                │
│     wic_admin_war_exploded.zip                            │
│     wic_pub_war_exploded.zip                              │
│     wic-admin-web.zip                                     │
│     wic-pub-startup-web.zip                               │
│                                                            │
│   [ 开始打包 ]     ← 预检全过才可点；不过时按钮禁用并说明原因   │
│   进度条 + 实时日志                                          │
└───────────────────────────────────────────────────────────┘

┌─ 配置页（一次性，向导式三步）───────────────────────────────┐
│  第 1 步  代码放哪？    [选择目录…]  → 自动扫描发现项目         │
│  第 2 步  打哪些模块？  勾选（自动发现的结果，可手动增删）        │
│  第 3 步  用什么工具链？  JDK/Maven 下拉（自动探测）+ 输出目录   │
└───────────────────────────────────────────────────────────┘
```

**分离后的收益**：日常只停在「打包」页，看到的是一份体检报告 + 一个按钮；
配置页只在第一次（或换项目时）进一次。

## 3. 让它“傻瓜”的四个具体机制

### 3.1 自动扫描发现项目（替代“必须先导入配置”）

配置页第 1 步选完代码根目录后，**自动扫描**并给出发现结果，用户只需要确认：

```
扫描 D:\code …
发现 6 个项目：
  ✓ wic-sh          2 个后端模块 + 2 个前端模块
  ✓ datax-web       1 个后端模块 + 1 个前端模块
  ○ seatunnel       3 个后端模块（未勾选）
  …
```

扫描规则（详见 §4）：找聚合 `pom.xml` 得后端模块；找 `package.json` 的 build 脚本得前端模块。

这样即使没有现成的 `bundle-packer` 配置，也不需要用户手抄模块清单——
这正是“扫库”的意义。既有的「导入配置…」保留作为补充路径。

### 3.2 预检清单（把失败拦在点击之前）

打包失败最气人的是「跑了 2 分钟才告诉你不该开始」。预检把所有前置条件
在点击前查一遍，逐条给出 ✓/✗ + **不通过时的修复建议**：

| 检查项 | 不通过时的提示 |
| --- | --- |
| JDK 可用 | 未找到 JDK：请安装，或在配置页手动指定路径 |
| Maven 可用 | 有后端模块但没找到 Maven：请安装 Maven 或指定 mvn.cmd |
| npm 可用 | 有前端模块但 PATH 里没有 npm：请安装 Node.js |
| 代码根目录存在 | 目录不存在：D:\code（配置页第 1 步可改） |
| 输出目录可写 | 目录不可写：换一个位置 |
| 模块目录完整 | `wic-admin` 下没有 pom.xml：检查模块路径 |
| 前端脚本已配置 | `wic-admin-web` 没有构建脚本：配置页第 2 步选择 |

**只有全部关键项通过，打包按钮才可点**；否则按钮禁用并把原因显示在按钮旁。

### 3.3 「本次将产出」清单

明明白白列出将要生成的每个 zip 文件名。用户点之前就知道会得到什么，
事后也能对照产物目录核对——避免「打完了但不知道打出了啥」。

### 3.4 配置页的默认值全部预填

- 代码根目录：若本机有 `D:\code` 之类常见目录且存在，作为默认值
- 保留环境：默认 `prod`
- 工具链：自动探测结果里最优的那个（真实 Maven 优先于项目 wrapper）
- 输出目录：记住上次用过的

用户在第 1、3 步通常只需要点「下一步/确认」，不用输入任何路径。

## 4. 项目自动扫描规则

```
输入：代码根目录，扫描深度上限（默认 3 层）

后端模块
  1. 遍历找 pom.xml（跳过 target/ node_modules/ .git/ .idea/ out/）
  2. 解析 pom：<packaging> 与 <modules><module>…
  3. 含 <modules> 的 pom 视为【项目根】（聚合模块），其 <module> 条目 → 后端模块
     不含 <modules> 的 pom 若其父目录不是项目根 → 视为独立项目（单模块）

前端模块
  4. 在项目根下（≤2 层）找 package.json（跳过 node_modules）
  5. 从 scripts 里挑构建脚本，优先级：
       build:prod > *build-prod* > *build* > build
     （本机实测 wic-admin-web 的脚本叫 "admin build:prod"、wic-pub-startup-web 的
      叫 "wic-startup-build-prod"，命名不统一，因此按模式匹配而不是固定名）
  6. 产物目录推断：有 vite.config.* → dist；package.json 里 build 脚本含 --outDir → 取该值；默认 dist

输出：项目列表（含模块清单、类型、脚本、产物目录）+ 扫描提示（无法解析的 pom 等）
```

**不确定的一律标注而不是猜死**：无法确定脚本的模块标记出来，让用户在配置页选，
而不是默默用错脚本打出错包。

## 5. 实现边界

### 本版实现

- ✅ 部署页拆为「打包 / 配置」两个页签，默认停在「打包」
- ✅ 自动扫描发现项目与模块（含脚本优先级匹配、产物目录推断）
- ✅ 预检清单（7 类检查 + 修复建议）+ 按钮按预检结果启用/禁用
- ✅ 「本次将产出」清单
- ✅ 配置页三步向导（选择目录 → 确认模块 → 工具链与输出目录）
- ✅ 未配置时的空状态引导（不显示一堆空表单，直接给一个「开始配置」按钮）

### 后续

- ⬜ 上次打包结果对比（产物大小、耗时变化）
- ⬜ 一键部署（把产物推送到目标服务器）
