## 4. 几个必须单独说明的发现

### 4.1 Docker 是 C 盘的头号黑洞：单文件 36.6 GB

```
%LOCALAPPDATA%\Docker\                                    36,904 MB
└── wsl\
    ├── disk\docker_data.vhdx                            36,650 MB   ← 就是它
    └── main\ext4.vhdx                                       96 MB
```

**一个 VHDX 文件占了 C 盘的 15.7%。** 这是 WSL2 后端 Docker 的数据盘。

**为什么这是设计上必须单独处理的一类**：

1. **它不在任何 Known Folder 里**，也不在注册表里，只能靠「遍历 `%LOCALAPPDATA%` + 识别 `.vhdx`」发现。
2. **删了等于删掉所有镜像、容器、卷** —— 是**用户数据**，绝不能标 L2。
3. **但它有两条正确的处理路径**：
   - **迁移**：Docker Desktop 设置里可直接改「Disk image location」到 D 盘（官方支持，最干净）。
   - **收缩**：VHDX 是**动态扩展**的，删除镜像/容器后**文件不会自动变小**。需要 `docker system prune -a` 之后用 `Optimize-VHD`（Hyper-V 模块）或 `diskpart compact vdisk` 才能真正释放。**这是一个「看起来没救其实能救回几十 GB」的典型场景**，工具应当在报告中明确指出。
4. **同类还有**：WSL2 的发行版根盘（`%LOCALAPPDATA%\Packages\*\LocalState\ext4.vhdx`）、Hyper-V 虚拟机磁盘、Windows Sandbox。

**设计含义**：
- 新增 `PathKind` 语义：`vhd`（虚拟磁盘），归 L3（仅报告）+ **强制迁移建议**
- 规则库需要一类**通用 VHDX 探测器**（不只是针对 Docker）：凡 `*.vhdx`/`*.vhd` 文件，一律 L3 + 建议迁移，且标注「动态扩展，实际使用量可能远小于文件大小」
- 报告需要「可收缩空间」的概念：`docker system prune` + `Optimize-VHD` 能回收多少

### 4.2 `pagefile.sys` 24.3 GB

**不能删**（L0），但可以在「系统属性 → 高级 → 性能 → 虚拟内存」里改到 D 盘。这是**本机最容易拿回的一块（24 GB）**。

设计含义：
- 需新增算子类型 `ChangeSystemSetting`（不是文件操作）
- 需要能解释「保留 C 盘最小分页文件（用于崩溃转储）还是完全移到 D 盘」的取舍
- 需要管理员权限

### 4.3 `hiberfil.sys` 9.7 GB

对应 `powercfg /h off`，可逆（`/h on`）。同样是 `ChangeSystemSetting` 算子。

### 4.4 JetBrains 存在跨版本索引缓存：9.4 GB

```
%LOCALAPPDATA%\JetBrains\IntelliJIdea2024.3    6,336 MB   ← 当前在用
%LOCALAPPDATA%\JetBrains\IntelliJIdea2022.2    3,052 MB   ← 旧版本，大概率已不启动
%LOCALAPPDATA%\JetBrains\Transient                114 MB
```

**这是「时间维度」的清理机会**：旧版本 IDE 的索引缓存是纯派生数据（重建即可），但**不能仅凭版本号旧就自动建议删除**——用户可能仍保留旧版本 IDE。判定需要：
- 检查该版本 IDE 的**主程序是否还存在**（在 `%LOCALAPPDATA%\Programs\` 或 JetBrains Toolbox 的安装目录下）
- 检查该缓存目录的 **mtime**（长期未访问才算旧）
- 因主程序是否存在的判断涉及 `install` 路径发现，属于 M2+M6 的交叉能力

设计含义：`cleanability` 需要一个**「孤儿缓存」（orphan cache）判定**子能力——缓存目录存在但对应的软件主程序/版本已不存在。这是高价值且安全的类别（`L1` → 可提升为 `L2` 若主程序确认不存在）。

### 4.5 重复/多处的同类缓存

| 现象 | 实例 | 设计含义 |
| --- | --- | --- |
| 同一软件的缓存出现在两个位置 | `Local\npm-cache`(306 MB) + `Roaming\npm-cache`(1.0 GB) | 必须**枚举全部候选位置**，不能取第一个命中 |
| 多个 AI/自动化工具各自下载浏览器二进制 | `ms-playwright`(740 MB) + `Cypress`(626 MB) + `.cache\puppeteer`(2.7 GB) + `.cache\chrome-devtools-mcp`(143 MB) | **合计 4.2 GB**。规则库应对「浏览器二进制缓存」建模为一类，并给出「多个工具重复下载同一 Chromium」的洞察 |
| 更新包残留散落各处 | `@mmx-agentelectron-updater`、`termius-updater`、`Docker Desktop Installer`、`Programs` 下的旧版本 | 规则库需要 `*-updater`、`* Installer`、`*Setup*` 等命名模式 |

### 4.6 `~\.cache` —— 传统清理工具完全盲区的类别

```
~\.cache\puppeteer              2,703 MB   Puppeteer 下载的 Chromium
~\.cache\codex-runtimes           781 MB   AI CLI 下载的运行时
~\.cache\chrome-devtools-mcp      143 MB
```
**合计 3.5 GB，且 `CCleaner`/`Windows 存储感知` 一个都不会报。** 这是本工具相对传统清理软件的**核心差异化价值**：规则库必须覆盖现代开发/AI 工具的缓存布局（`~/.cache/<tool>` 是 Linux 惯例在 Windows 上的渗透结果）。

## 5. 从中得出的设计结论（映射到文档）

| 实测事实 | 设计结论 | 落在哪篇 |
| --- | --- | --- |
| 可安全删除的传统垃圾仅 ≈1.5 GB，而 C 盘缺 3.9 GB 中的大头是 Docker 36.6 GB / pagefile 24.3 GB / hiberfil 9.7 GB | **工具定位必须是「空间治理」而非「垃圾清理」**；迁移与系统设置调整是主力，删除是辅助 | `README`、`01` |
| 4 类最佳收益都是「迁移」或「功能调整」，不是删除 | `migratability` 与 `ChangeSystemSetting` 算子是一等公民，不是附加功能 | `01`、`07` |
| Docker VHDX 36.6 GB 只能靠「改配置迁移 + 压缩 VHDX」处理 | 需要 `vhd` 路径类型、`Optimize-VHD` 建议、通用 VHDX 探测器 | `05`、`06`、`07` |
| `InstallLocation` 缺失率 67% | 必须有反推算法（`DisplayIcon`→`UninstallString`→启发式），且要记录来源与置信度 | `04` §3.2 |
| 卸载表混入 Chrome 扩展（`GoFullPage`、`文档`） | 必须有非软件条目过滤规则 | `04` §1 事实 2 |
| 非管理员可读全部 HKLM 卸载表（61 + 128 项） | 扫描阶段**不提权**，符合 NFR-3 | `04` §1 事实 3、`09` |
| `Desktop`/`Pictures` 已被 OneDrive 接管，`Downloads` 未接管 | 必须检测 OneDrive 接管并默认排除迁移；`Downloads` 是首选重定向目标 | `05` §3.3/§3.4 |
| `图片` 在 GBK 控制台下显示为 `ͼƬ` | 全链路 UTF-16↔UTF-8，禁止 ANSI 代码页 | `03` §2.2、`09` |
| `~/.cache/puppeteer`、`ms-playwright`、`Cypress` 等传统工具盲区 | 规则库必须覆盖开发/AI 工具缓存，且要有通用 `~/.cache/*` 与二进制缓存建模 | `05`、`10` |
| 同一软件缓存出现两处（npm） | 路径发现必须枚举全部候选，不能取首命中 | `05` §6.2 |
| JetBrains 旧版本索引 3.0 GB | 需要「孤儿缓存」判定（主程序不存在 → 缓存可清） | `06` §6.8 |
| `secoresdk` 857 MB 未识别 | 未识别目录必须上报为 L3，并提示可提交规则 | `05` §7.4 |
| 约 16 GB 因无管理员权限无法归因 | 报告必须显式标注归因缺口与覆盖率 | `03` §8、`09` |

## 11. 作为测试 fixture 的使用方式

1. **`testdata/registry/`**：把本机卸载表导出为 JSON（§9），作为注册表解析与反推算法的测试输入。特别要保留 4 个负例：`GoFullPage ...`、`文档`、`WPS Office (12.1.0.28505)`、`零信浏览器`。
2. **`testdata/scan_cases/`**：从本机采集一份**脱敏的目录树快照**（路径 + 大小 + mtime + 属性，不含文件内容），作为 golden 测试输入。因为它是真实的，能捕捉到合成数据无法覆盖的怪路径（中文、超长、reparse）。
3. **等级回归**：每次改规则库后，在这份快照上重跑判定，**diff 等级变化**。任何从 L0/L1 降到 L2 的变化必须人工 review。这是防止「改规则改出安全问题」的核心机制。
4. **未识别率指标**：本机 207 条中 `category == unknown` 的比例作为规则库完善度的量化指标，目标 < 20%。
5. **验收基准**：§10 的预期基线即 M5 的验收标准。
