# 04 — 软件识别与清单

目标：回答「这台机器上装了什么软件、每个是干嘛的、装在哪个盘」。这份清单随后被 `attribution`（空间归因）与 `cleanability`/`migratability`（判定）消费。

---

## 1. 本机实测的关键事实（决定了整个设计的走向）

在动手设计前对本机实测，得到三个必须写进代码的现实：

### 事实 1：`InstallLocation` 缺失率约 **67%**

HKCU 卸载表 15 个条目中，只有 5 个有 `InstallLocation`：

| DisplayName | HasInstallLocation | HasUninstallString |
| --- | --- | --- |
| SwitchHosts 4.1.1 | ❌ | ✅ |
| ZCode 3.9.2 | ❌ | ✅ |
| Termius 9.31.4 | ❌ | ✅ |
| DBeaver 22.3.2 (current user) | ❌ | ✅ |
| 飞书 | ❌ | ✅ |
| WPS Office (12.1.0.28505) | ❌ | ✅ |
| MiniMax Code 3.0.65 | ❌ | ✅ |
| Claude Code | ✅ | ✅ |
| Clash Verge | ✅ | ✅ |
| Postman x64 11.87.4 | ✅ | ✅ |
| Python 3.14.6 | ✅ | ✅ |
| 零信浏览器 | ✅ | ✅ |
| Microsoft Visual Studio Code (User) | ✅ | ✅ |

**结论**：`InstallLocation` 只能当作**提示**，绝不能当作唯一来源。必须有 `UninstallString` / `DisplayIcon` / `QuietUninstallString` 的**反推算法**（见 §3.2），且反推失败时要退化为「按目录名在已知安装根下探测」。

### 事实 2：卸载表里混着**非软件**条目

本机 HKCU 卸载表里出现了：

- `GoFullPage - Full Page Screen Capture Chrome Extension`（Publisher = `Google\Chrome`）
- `文档`（Publisher = `Google\Chrome`）

这两个是 **Chrome 扩展**，不是独立软件。它们会污染「软件清单」，让用户看到一堆没意义的条目，也会让归因逻辑把它们当成独立 App 去匹配规则库（必然匹配失败）。

**过滤规则**：
```
排除条件（满足任一即从清单剔除，但保留在原始数据中供 debug）：
- Publisher 匹配 `^Google\\Chrome$` / `^Mozilla` 且 DisplayName 含 `Extension`
- DisplayName 匹配 `(?i)(extension|插件|theme|主题)$`
- 无 UninstallString 且无 InstallLocation 且无 EstimatedSize
- ParentKeyName / ParentDisplayName 存在（明确的子组件）
- SystemComponent == 1（系统的隐藏组件）
```

### 事实 3：**普通用户即可读 HKLM 卸载表，无需管理员权限**

实测（当前进程 `IsInRole(Administrator) == false`）：

| 键 | 条目数 |
| --- | --- |
| `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` | 61 |
| `HKLM\SOFTWARE\WOW6432Node\...\Uninstall` | 128 |
| `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` | 18 |
| **合计（去重前）** | **207** |

**结论**：扫描阶段**不需要管理员权限**（符合 NFR-3 与 ADR/约束）。这对用户体验很重要——扫描可以随时跑，不会每次都弹 UAC。

## 2. 五类数据源

按优先级从高到低，全部采集后合并。

### 2.1 HKLM 卸载表（64 位）— 系统级安装
- 路径：`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*`
- 特点：多为 `Program Files` 下的传统安装，**存储在 C 盘的比例高**（这是 C 盘压力的一大来源）
- 本机 61 项

### 2.2 HKLM 卸载表（32 位 / WOW6432Node）
- 路径：`HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*`
- 特点：32 位程序；条目数往往最多（本机 128 项）
- **坑**：同一个软件可能同时出现在两个位置 → 必须去重

### 2.3 HKCU 卸载表 — 当前用户安装
- 路径：`HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*`
- 特点：**per-user 安装的重灾区**。Squirrel/Electron 系（VS Code、Discord、Slack、飞书、ZCode、Claude Code、Termius…）几乎全部在这里
- **子键名形态**值得注意（本机实测三种）：
  - GUID：`0fe234d9-0d04-586e-929c-f74ec824c6ec`（Squirrel 风格）
  - 十六进制哈希：`2b27a2258069f4176ce5201ebdf0f631`
  - 可读名：直接是软件名
  - **不要从子键名推断任何东西**，一切以键值为准
- 本机 18 项

### 2.4 Microsoft Store / UWP 应用
两条路线：

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 注册表 `HKCU\Software\Classes\Local Settings\Software\Microsoft\Windows\CurrentVersion\AppModel\Repository\Packages` | 纯注册表，无进程开销，快 | 字段较原始，需自行解析 `PackageFullName` |
| PowerShell `Get-AppxPackage` | 字段齐全 | 需启动 PowerShell，慢（1–3 s），可能被执行策略阻止 |

**选择**：以注册表为主（快、无依赖、离线可用），PowerShell 作为 `--deep` 模式的补充。

UWP 应用的安装位置固定在 `C:\Program Files\WindowsApps`，**该目录受系统保护**（ACL 拒绝访问，且里面的目录是 reparse point）——遍历时必须跳过，`cleanability` 中直接标 L0。

### 2.5 便携 / 绿色软件（无注册表记录）
本机有明显的便携软件踪迹：`D:\workplace\switchHost\SwitchHosts`（虽有注册表）、`D:\softw...`、`D:\packages`。用户手工放在 D 盘的软件很多没有注册表记录。

识别方式（按置信度排序）：
1. **规则库路径匹配**：规则库声明某软件「便携版通常在这个目录」，如 `%LOCALAPPDATA%\Programs\*`
2. **特征文件探测**：在已知安装根的一级子目录下寻找 `*.exe` + 常见伴生文件（`LICENSE`、`*version*`、`resources\app`）
3. **`%LOCALAPPDATA%\Programs`**：这是 per-user 便携软件的约定目录，必扫
4. 置信度 < 阈值的标记为 `unknown`，**只参与归因，不参与清理判定**（符合 ADR/原则 3）

### 2.6 游戏平台库
配置文件驱动的枚举（不扫盘就能拿到完整列表）：

| 平台 | 配置文件 | 解析要点 |
| --- | --- | --- |
| Steam | `steamapps\libraryfolders.vdf` + 各库的 `appmanifest_*.acf` | VDF 格式（KeyValues），需轻量解析器；`libraryfolders.vdf` 列出所有库路径 → 能一次拿到「Steam 库分散在 C/D 盘的哪些位置」 |
| Epic | `%ProgramData%\Epic\UnrealEngineLauncher\LauncherInstalled.dat` (JSON) | 直接可解析 |
| Battle.net / Riot / GOG | 各有配置或注册表 | P2，后续补 |

**为什么单独做**：游戏动辄 50–150 GB，是「空间去哪了」的头号答案，而它们通常**不在卸载表里**（或只在注册表里留一条无路径的记录）。

## 3. 字段提取

### 3.1 标准字段

| 输出字段 | 注册表来源 | 坑 |
| --- | --- | --- |
| `DisplayName` | `DisplayName` | 可能含版本号后缀（`WPS Office (12.1.0.28505)`、`DBeaver 22.3.2 (current user)`）→ 需剥离以利于规则库匹配 |
| `Publisher` | `Publisher` | 可能为空；可能是 `Google\Chrome` 这种（见事实 2） |
| `Version` | `DisplayVersion` | 缺失常见 |
| `InstallDate` | `InstallDate` | 格式 `YYYYMMDD`，无分隔符 |
| `EstimatedSize` | `EstimatedSize` (`REG_DWORD`) | **单位是 KB 不是字节**；经常缺失；且常常严重不准（只算主程序目录，不含用户数据）→ **只作为兜底，实际大小一律用扫描结果** |
| `UninstallString` | `UninstallString` | 见 §3.2 |
| `DisplayIcon` | `DisplayIcon` | 见 §3.2 |
| `InstallLocation` | `InstallLocation` | 67% 缺失（事实 1） |
| `SystemComponent` | `SystemComponent` | `1` = 系统隐藏组件，应过滤 |
| `ParentKeyName` | `ParentKeyName` | 存在 = 子组件，应过滤 |
| `WindowsInstaller` | `WindowsInstaller` | `1` = MSI 安装，其缓存位于 `C:\Windows\Installer`（L0，不可动） |

### 3.2 安装目录反推算法（因为 67% 缺失，这是必需逻辑）

按顺序尝试，任一步成功即停止：

```
输入：DisplayIcon, UninstallString, QuietUninstallString, DisplayName

步骤 1 — 从 DisplayIcon 反推（最可靠）
  DisplayIcon 形如 "C:\Program Files\App\app.exe,0"
  → 去掉 ",<index>" 后缀 → 取 dirname
  → 若结果是 \Application、\bin、\current 等子目录，向上冒泡到有意义的根
     （例：Chrome 的 DisplayIcon 指向 ...\Chrome\Application\chrome.exe
       应归到 ...\Chrome 而非 ...\Chrome\Application）

步骤 2 — 从 UninstallString 反推
  形如 "C:\Program Files\App\unins000.exe" /SILENT
  → 提取第一个引号内的路径 → dirname
  → 若文件名含 unins/uninstall/Uninstall，则 dirname 即为安装目录
  → 注意 Squirrel 风格：...\AppName\Update.exe --uninstall
    此时 dirname 是更新器目录，安装根应为它的父级

步骤 3 — 从 QuietUninstallString 反推（同上）

步骤 4 — MSI 产品码反推
  若 WindowsInstaller == 1 且 UninstallString 含 {GUID}
  → 该软件的真实位置只能靠扫描归因，无法从注册表得到
  → 标记 InstallLocationSource = Unknown

步骤 5 — 按名字在已知安装根下探测
  候选根：%ProgramFiles%, %ProgramFiles(x86)%, %LOCALAPPDATA%\Programs,
          %APPDATA%, %LOCALAPPDATA%, D:\*（用户自定义盘）
  用 DisplayName 清洗后的名字做模糊匹配（归一化：小写、去空格、去版本号）
  → 命中则采用，InstallLocationSource = Heuristic

步骤 6 — 放弃
  InstallLocation = ""，InstallLocationSource = NotFound
  → 该 App 仍参与清单展示，但空间归因完全依赖规则库路径 + 目录名匹配
```

**必须记录 `InstallLocationSource`**，因为后续判定要按来源给不同置信度（`Unknown`/`Heuristic` 来源的路径不能用于 L2 清理判定）。

### 3.3 从注册表拿不到的、必须靠扫描补的东西

| 信息 | 为什么拿不到 | 怎么补 |
| --- | --- | --- |
| **真实占用空间** | `EstimatedSize` 不准且只算程序目录 | 扫描（`03`），并把用户数据目录一起归因 |
| **用户数据目录** | 注册表完全不记录 | 规则库路径模板 + 启发式（`05`） |
| **软件用途** | 注册表不记录 | 规则库（`10`），兜底用 Publisher + 名称推断 |
| **是否便携版** | 无记录 | 特征文件探测（§2.5） |
| **配套服务/自启动** | 需查 `Run` 键与服务表 | P2，本期不做 |

## 4. 用途与分类（回答「这软件是干嘛的」）

注册表没有任何「用途」信息，必须靠规则库。规则库为每个 `AppRule` 提供：

```yaml
id: google.chrome
display_name: Google Chrome
aliases: ["Chrome", "Google Chrome"]
publisher: Google LLC
category: browser          # ← 分类枚举
purpose: "网页浏览器，用于访问互联网站点"   # ← 一句话用途，中文
homepage: https://www.google.com/chrome/
```

### 4.1 分类枚举（Category）

设计为**有限枚举**，因为分类会被判定逻辑引用（例如「浏览器缓存」的清理规则按 category 匹配）：

| Category | 中文 | 典型 | 空间特征 |
| --- | --- | --- | --- |
| `system` | 系统组件 | Windows、驱动 | 空间大但不该动 |
| `browser` | 浏览器 | Chrome、Edge、零信浏览器 | 缓存可清，用户数据需迁 |
| `devtool` | 开发工具 | VS Code、Cursor、JetBrains、DBeaver、Postman、Clash Verge | 缓存多、体积大、最适合迁移 |
| `ai-tool` | AI 工具 | Claude Code、ZCode、MiniMax Code、Trae | **`.cache` 里的运行时下载是重灾区** |
| `im` | 即时通讯 | 微信、QQ、飞书、钉钉、Discord | **用户数据为主，不可删，需用软件内功能迁** |
| `office` | 办公 | WPS、Office、Xmind、Adobe | 缓存可清，插件数据需留 |
| `game` | 游戏 | Steam 库、Epic | 体积巨大，可迁移（但迁移代价高） |
| `media` | 影音图像 | 播放器、修图 | |
| `download-tool` | 下载/网盘 | 百度网盘、迅雷 | 下载目录是迁移重点 |
| `security` | 安全 | 杀软、VPN | **绝对不碰** |
| `runtime` | 运行时 | Python、JDK、Node、nvm、.NET | 可迁移（环境变量机制） |
| `utility` | 工具 | 压缩、截图、SwitchHosts、Termius | |
| `unknown` | 未识别 | — | 只归因，不判定 |

### 4.2 用途描述的兜底

规则库未命中时的降级链：

```
1. 规则库精确匹配（id / display_name / alias）→ purpose 完整
2. 规则库模糊匹配（归一化后前缀/子串 + publisher 匹配）→ purpose 完整，置信度略降
3. Publisher 已知（如 "Tencent"）→ 用 Publisher 级规则：用途 = "腾讯系软件（分类见详情）"
4. 完全未知 → category = unknown, purpose = "未识别的软件"
   并在报告中建议「可提交此条目以完善规则库」
```

**注意**：本机有中文软件（飞书、零信浏览器、文档、WPS），以及中文 Publisher。归一化必须正确处理中文（不能做 ASCII lowercase 就完事），且规则库的 `aliases` 要覆盖中文名与英文名（`飞书` / `Lark` / `Feishu`）。

## 5. 合并与去重

### 5.1 去重键（按优先级）

```
键 1：规范化后的 InstallLocation（去尾斜杠、小写、展开环境变量）
      → 同一目录出现多次，必然是同一软件的不同注册表视图

键 2：规范化（DisplayName 去版本号去空格小写） + Publisher
      → 解决「有路径」与「没路径」两条记录指向同一软件的情况

注意：只做保守合并。宁可留下两条让用户看到重复，
      也不能错误合并两个不同软件（会影响后续归因分摊）
```

### 5.2 来源优先级

合并时字段取值按来源优先级（高→低）：`HKCU` > `HKLM64` > `HKLM32` > `UWP` > `Portable` > `GameStore`。

**理由**：per-user 安装的信息通常更新更准（如 VS Code 的 User 安装），且用户实际运行的是这一份。冲突时保留高优先级来源的值，但**保留全部来源标记**：

```go
type AppSource string
const (
    SourceRegistryHKLM64 AppSource = "registry-hklm64"
    SourceRegistryHKLM32 AppSource = "registry-hklm32"
    SourceRegistryHKCU   AppSource = "registry-hkcu"
    SourceUWP            AppSource = "uwp"
    SourcePortable       AppSource = "portable"
    SourceGameStore      AppSource = "gamestore"
)
```

一个 App 可以同时来自多个源（`Sources []AppSource`），便于诊断。

### 5.3 冲突场景与处理

| 场景 | 处理 |
| --- | --- |
| 同一软件 32/64 位都有记录，路径相同 | 合并，`Sources` 记两个 |
| 同一软件 32/64 位都有记录，路径不同 | **不合并**，视为两个安装（报告里标注「疑似重复安装」——这本身就是可优化的空间） |
| 同一 DisplayName 但 Publisher 不同 | **不合并**（可能是不同厂商的同名软件） |
| 卸载表有记录但目录不存在 | 标记 `Orphaned=true`（**这是「卸载残留」，属于有价值的清理线索**，但归 L1 需确认） |

`Orphaned` 这个标记很重要：本机 67% 的条目没有 `InstallLocation`，反推出来的路径如果不存在，说明**软件已卸载但注册表残留**，或者反推失败了。两种情况都要在报告中区分（前者是清理线索，后者是识别缺陷）。

## 6. 输出模型

```go
type App struct {
    // 标识
    ID            string      // 规则库 ID，如 "google.chrome"；未识别为空
    DisplayName   string      // 规范化后的显示名
    RawName       string      // 注册表原始 DisplayName（保留原始值便于排查）
    Publisher     string
    Version       string
    InstallDate   time.Time

    // 来源
    Sources       []AppSource

    // 位置
    InstallLocation       string   // 反推结果，可能为空
    InstallLocationSource string   // displayicon / uninstallstring / heuristic / notfound
    InstallVolume         string   // "C" / "D" / "" —— 直接回答「装在哪个盘」

    // 知识（来自规则库）
    Category      Category   // browser / devtool / ...
    Purpose       string     // 一句话中文用途
    Homepage      string
    MatchedRule   string     // 命中的规则 ID + 匹配方式（精确/模糊/兜底）
    MatchConfidence float64

    // 空间（来自扫描归因）
    Dirs          []DirUsage // 关联的所有目录及占用
    TotalOnDisk   int64      // 实际占用合计
    TotalLogical  int64

    // 状态
    Orphaned      bool       // 注册表有、目录不存在
    Filtered      bool       // 被 §事实2 的规则过滤掉（非真正软件）
    FilterReason  string
}

type DirUsage struct {
    Path       string
    Kind       PathKind   // install / cache / data / config / download / log
    OnDisk     int64
    Logical    int64
    FileCount  int64
    Exists     bool
    Source     string     // 这个路径是怎么发现的（rule-id / heuristic / knownfolder）
    Confidence float64
}
```

## 7. 测试策略

| 测试 | 方式 |
| --- | --- |
| 注册表解析 | 把本机卸载表导出为 JSON fixture（`testdata/registry/`），单测解析与字段提取，**不依赖真实注册表** |
| 反推算法 | 表驱动测试：输入 `DisplayIcon`/`UninstallString` 的各种形态（带引号、带参数、Squirrel 风格、MSI 风格、中文路径），断言输出路径 |
| 过滤规则 | 用本机真实样本作为负例：`GoFullPage ... Chrome Extension`、`文档` 必须被过滤 |
| 去重 | 构造 32/64 位重复、路径相同/不同、同名不同 publisher 的用例 |
| UWP 解析 | `PackageFullName` 字符串解析的边界用例（含下划线、含 `~` 短哈希） |
| 分类与用途 | 规则库覆盖度测试：把本机 207 个条目跑一遍，统计 `category == unknown` 的比例，**目标 < 20%**，作为规则库完善度的量化指标 |
| 无权限 | 断言在非管理员下能读全 HKLM 卸载表（已实测可行） |
