# 09 — 安全与风险控制

这个工具的失败模式是**不可逆的数据丢失或系统损坏**。所以安全不是「注意一下」，而是必须用机制强制保证的东西。

**本期的安全优势**：M1–M6 全部是只读（扫描与分析），**零写操作**。但要说明的是——**设计必须在 M1 就把安全机制的结构定好**，因为 M7 的执行器会复用 `model` 与 `catalog`，如果早期没留好等级、journal、precheck 这些结构，后期补会牵动全局。

## 1. 权限模型

| 阶段 | 权限 | 实测依据 |
| --- | --- | --- |
| 扫描（M1） | **普通用户** | 已实测：非管理员下可读 HKLM(61) + WOW6432Node(128) + HKCU(18) 共 207 条卸载记录 |
| 软件清单（M2） | **普通用户** | 同上 |
| 路径发现（M3） | **普通用户** | Known Folder / 环境变量 / 用户级注册表都可读；WMI 卷信息可读 |
| 可清理性判定（M4） | **普通用户** | 纯计算 |
| 报告（M5） | **普通用户** | |
| 迁移计划生成（M6） | 普通用户（**预检需探测权限**，但不执行） | |
| 执行清理 / 迁移 / 系统设置（M7） | **按算子按需提权** | |

### 1.1 不提权运行是刻意的设计

理由：
1. **降低使用门槛**——用户随时可以跑 `scan` 看情况，不会每次弹 UAC。
2. **降低风险面**——不提权的进程即使有 bug，破坏范围也被系统 ACL 限制住（碰不到 `System32` 等）。
3. **心理接受度**——一个"分析工具"比一个"需要管理员权限的删除工具"更容易被信任和使用。

### 1.2 提权的实现（M7）

**不使用** `requireAdministrator` manifest（那会导致每次运行都弹 UAC，包括纯扫描）。而是：

- manifest 用 `asInvoker`
- 只在 `apply` 且算子确实需要提权时，用 `ShellExecuteW(..., "runas", ...)` **重新以管理员身份启动自己**，并把待执行的 plan 与 journal 路径作为参数传入
- 提权后的子进程只做执行，不重新扫描

```go
// 需要提权时的自举
ShellExecuteW(nil, "runas", os.Args[0],
    "--internal-apply --plan plan.json --journal journal.json", nil, SW_SHOWNORMAL)
```

### 1.3 部分提权场景的处理

有些算子不需要管理员（环境变量写 `HKCU`、Junction 在本地卷内、`%LOCALAPPDATA%` 下的文件），有些需要（页面文件、休眠、`HKLM`、`System32` 下的清理）。

**设计**：`apply` 支持**分批执行**——先跑不需要提权的算子，再提示用户「以下 N 个算子需要管理员权限，是否提权执行？」。这样用户可以只用不提权的部分。

## 2. 路径安全校验（防止操作跑到预期之外）

每一次对路径的操作（扫描、判定、删除、迁移）之前，必须经过统一校验函数。**没有例外。**

```go
// sys/safe_path.go
type PathValidation struct {
    OK       bool
    Reason   string
    // 解析产物
    Input        string   // 原始输入
    Cleaned      string   // Clean 之后
    Absolute     string   // 绝对路径
    Extended     string   // \\?\ 形式
    Canonical    string   // 规范化（大小写、短名展开、符号解析后），用于比较
    Volume       string   // "C"
    IsReparse    bool
    ReparseTag   uint32
    LinkTarget   string
}

func ValidatePath(input string) (PathValidation, error)
```

### 2.1 校验清单

| 检查 | 失败处理 |
| --- | --- |
| 输入非空 | 拒绝 |
| 不含 NUL 字节 | 拒绝（Windows API 会截断） |
| `filepath.Clean` 后不含 `..` 逃逸 | 拒绝 |
| 是绝对路径（或有明确的基准目录） | 若无基准，拒绝 |
| 驱动器存在且是固定盘（除非显式允许其他类型） | 拒绝 |
| 短名（8.3）→ 展开为长名，且长名也通过校验 | 拒绝（`C:\PROGRA~1` 绕过白名单是经典手法） |
| 大小写规范化（用于比较） | — |
| **不在被禁止的根之列**（见 §3） | 拒绝 |
| 若在允许的根内，规范化后仍必须在根内 | 拒绝 |
| 若是 reparse point，解析其目标并对目标重复上述校验 | 按上下文处理（§2.2） |

### 2.2 关于 reparse point 的解析

存在一个两难：
- **不解析**：`C:\Users\me\Desktop` 若是指向 `D:\OneDrive\Desktop` 的链接，操作会落到 D 盘，但我们的白名单校验是基于 `C:\Users\me\Desktop` 这个字符串做的 → **校验被绕过**。
- **解析**：如果解析后就拒绝了，那 Junction 迁移后就无法再操作那些路径了（因为所有迁移后的路径都是 Junction）。

**方案**：
```go
// 校验分两层，用途不同
// 层 1：字符串层校验 —— 始终基于用户传入/规则声明的路径（用于"这个路径是否在我们允许操作的范围内"）
// 层 2：物理层校验 —— 解析 reparse 后的真实路径（用于"我们实际要动的是哪个物理位置"）

// 两条规则：
// 规则 A：任何"删除"动作，其物理目标必须也通过层 1 校验。
//        即：不允许通过链接把删除引导到白名单之外的位置。
//        → 删除前解析 reparse，若物理目标不在允许范围 → 拒绝
// 规则 B：Junction 本身是允许的最终状态（迁移产物），
//        但创建 Junction 时，其目标必须通过层 1 校验。
//        → 创建 Junction 前校验 target
```

这条「规则 A」是防越界删除的关键：**它阻止了"通过一个被植入的链接把删除操作引到 C:\Windows"这类攻击或误操作**。

### 2.3 长路径与 `\\?\` 的双重作用

`\\?\` 前缀除了突破 260 字符限制，还有一个安全副作用：**它禁用路径规范化**。这意味着 `\\?\C:\a\..\..\Windows` 会被当作字面量路径（`a` 下叫 `..` 的目录），不会被解析成 `C:\Windows`。

所以正确的顺序是：
```
1. 用户输入 → filepath.Clean（在我们控制的代码里规范化，明确知道在做什么）
2. → 校验（此时路径已 Clean，无 .. 逃逸）
3. → 转 \\?\ 形式（此后 Windows 不再做任何隐式解析）
4. → 传给 API
```
**绝不允许**把未经 Clean 的输入直接加 `\\?\` 前缀——那只是掩盖问题。

## 3. 禁止操作的根（硬编码，不可配置绕过）

```go
// 这些根及其所有后代，永不接受任何写操作（读取与统计允许）
var forbiddenWriteRoots = []string{
    `C:\Windows`,
    `C:\Program Files`,
    `C:\Program Files (x86)`,
    `C:\ProgramData\Microsoft\Windows\Start Menu`,
    `C:\Recovery`,
    `C:\$Recycle.Bin`,              // 内容不直接删，走 Shell API 清空
    `C:\System Volume Information`,
    // 所有其他卷上的等价系统目录
}
// 例外（白名单，需显式枚举，不允许通配）：
var allowedWriteExceptions = []string{
    `C:\Windows\Temp`,                            // 临时文件
    `C:\Windows\Logs\CBS`,
    `C:\Windows\Logs\DISM`,
    `C:\Windows\Logs\WindowsUpdate`,
    `C:\Windows\SoftwareDistribution\Download`,   // 需先停 wuauserv
    `C:\Windows\LiveKernelReports`,
    `C:\Windows\Minidump`,
}
```

**注意例外清单的写法**：必须是**显式枚举的具体路径**，不允许出现 `C:\Windows\Logs\*` 这种通配——通配会随 Windows 版本变化而扩大暴露面。

**对称性测试**：`TestForbiddenRootsHaveNoWildcardExceptions` —— 断言例外清单里没有通配符，且每条例外都是禁止根的后代。

## 4. 删除的安全护栏（M7 用，本期定义）

虽然本期不实现删除，但护栏规则必须现在定好，因为它们会影响 `plan` 的生成逻辑（例如：plan 生成时就要检查「这个算子的删除量是否超过阈值」并提前预警）。

### 4.1 数量与体量阈值

| 护栏 | 阈值（默认） | 行为 |
| --- | --- | --- |
| 单算子删除文件数 | > 10,000 | 需显式 `--yes-i-know` 或交互确认 |
| 单算子删除体积 | > 5 GB | 同上 |
| 整个 plan 的删除体积 | > 20 GB | 需二次确认 |
| 单算子删除目录树深度 | > 8 层 | 警告（可能误删父目录） |
| 涉及 L1 的数量 | > 0 | 必须逐项确认（不接受 `--yes` 一次性通过） |

### 4.2 删除顺序

```
自底向上（先文件后目录），且在每一层删除前重新验证：
  1. 该路径仍通过 ValidatePath
  2. 该路径仍存在于扫描结果中（防 TOCTOU——扫描与执行之间文件可能已被替换）
  3. 该路径的等级仍是 L2（从 plan 读，但 plan 里存的等级要与当前规则库版本一致）
  4. 该路径不是 reparse point（§4.4 of 07）
  5. 该路径未被占用（M7 时实时检测）
```

**TOCTOU 问题的处理**：扫描与执行之间可能经过很长时间（用户审阅 plan），期间文件系统可能变化。所以**每条删除动作执行前必须重新做一次轻量校验**（存在性、是否 reparse、是否被占用），而不能只信 plan.json 里的快照。

**最危险的情形**：扫描时 `C:\Users\me\AppData\Local\SomeApp\Cache` 是一个真实目录（判为 L2），但执行前用户（或恶意程序）把它替换成了一个指向 `C:\Windows` 的 Junction。此时若无重校验，递归删除会摧毁系统。这就是为什么第 4 条检查必须在**执行时**做，而不是只在扫描时做。

### 4.3 回收站策略

| 策略 | 说明 |
| --- | --- |
| **默认：直接删除，不进回收站** | 理由：这些是缓存/临时文件，进回收站毫无意义，而且回收站本身还占 C 盘空间（与目标矛盾） |
| L1 项：**可选进回收站** | 用户可能想恢复。用 `SHFileOperation` + `FOF_ALLOWUNDO` |
| 超过回收站容量时 | Windows 会直接永久删除，需提示用户 |

**结论**：L2 直接删（因为这些文件的价值就是可重建），L1 默认进回收站或要求显式确认永久删除。

### 4.4 禁止的 API 使用

在 CI 里用 grep 强制检查，出现即 CI 失败：

| 禁止 | 原因 | 替代 |
| --- | --- | --- |
| `os.RemoveAll` | 会递归跟随 reparse point 删掉链接目标 | 自实现的 `SafeRemoveTree`，带 reparse 检查 |
| `filepath.Walk` / `WalkDir` | 无法控制 reparse point 行为，无法拿到 FileIndex/OnDiskSize | 自实现的 `SafeWalker` |
| `os.ExpandEnv` | 静默把未定义变量替换为空串，可能生成相对路径 | 自实现的 `ExpandVars`（未定义即报错） |
| `exec.Command("cmd", "/c", ...)` 且参数含用户输入 | 命令注入 | 用 `exec.Command` 直接传参数数组；确需 shell 时严格白名单 |
| `os.MkdirAll` 在未校验的路径上 | 可能在校验范围外创建目录 | 先 `ValidatePath` |
| 直接拼 SQL 式的注册表路径 | 路径注入 | 转义或使用 registry 包的 API |

### 4.5 命令执行的额外约束（针对 `RunCommand` 算子）

`npm cache clean --force` 这类算子有命令注入风险。

```go
// 算子中存的是结构化命令，不是字符串
type Operator struct {
    // ...
    Command string   `json:"command"`   // 只允许白名单内的可执行文件名
    Args    []string `json:"args"`      // 参数数组，不经过 shell
}

var allowedCommands = map[string]AllowedCommand{
    "npm":         {Path: "npm.cmd", AllowedArgs: []string{"cache clean --force"}},
    "pip":         {Path: "pip.exe", AllowedArgs: []string{"cache purge"}},
    "yarn":        {Path: "yarn.cmd", AllowedArgs: []string{"cache clean"}},
    "docker":      {Path: "docker.exe", AllowedArgs: []string{"system prune -a --volumes", "builder prune -a"}},
    "powercfg":    {Path: "powercfg.exe", AllowedArgs: []string{"/h off", "/h on", "/h /size 40"}},
    "Optimize-VHD": {Path: "powershell.exe", AllowedArgs: []string{"-Command Optimize-VHD -Path * -Mode Full"}},
}
// 白名单校验：命令存在 + 参数组合在白名单内 + 路径参数必须是 ValidatePath 通过的绝对路径
```

**关键**：`exec.Command` 在 Windows 上不经过 shell（不像 Unix 的 sh -c），所以参数数组本身是安全的。风险主要来自**允许用户自定义命令**——所以规则库里的命令是**内置的常量**，不接受用户输入拼接。

## 5. 编码与路径正确性

### 5.1 实测到的坑

本机侦察时，PowerShell 输出的 `C:\Users\33380\OneDrive\图片` 在 GBK 控制台下显示成了 `OneDrive\ͼƬ`。这证明了**编码问题是真实存在的**，不是理论担忧。

### 5.2 规则

| 规则 | 说明 |
| --- | --- |
| **Go 内部一律用 UTF-8 字符串** | Go 的 `string` 是 UTF-8，天然正确 |
| **调用 Windows W 系列 API** | 只用 `...W` 后缀的 API（`FindFirstFileExW`、`CreateFileW`、`GetVolumeInformationW`），绝不用 A 系列（ANSI） |
| **UTF-16 ↔ UTF-8 转换只用 `syscall.UTF16PtrFromString` / `UTF16ToString`** | 不要手写转换 |
| **控制台输出前设置代码页** | `SetConsoleOutputCP(CP_UTF8)`，或直接用 UTF-8 输出并让终端适配 |
| **绝不使用 ANSI 代码页解释路径** | 会破坏中文路径（`图片`、`微信`、`文档`、`飞书`、`零信浏览器`） |
| **JSON 输出用 UTF-8** | Go 标准库默认正确；注意 `encoding/json` 会把 `<`/`>`/`&` 转义为 `\u003c` 等，对路径无害但可读性差，可用 `Encoder.SetEscapeHTML(false)` |
| **文件名比较用大小写不敏感** | Windows 文件系统不区分大小写；但**保留原始大小写**用于展示 |
| **路径分隔符统一为 `\`** | 接受用户输入 `/` 与 `\`，内部统一转换为 `\` |

### 5.3 中文软件的规则匹配

本机有大量中文软件与中文 Publisher：

| 场景 | 要求 |
| --- | --- |
| DisplayName 是中文（`飞书`、`零信浏览器`、`文档`） | 归一化不能只做 ASCII 小写；中文不变，ASCII 部分小写 |
| 规则库 aliases 要含中英文 | `飞书` / `Feishu` / `Lark` / `LarkShell` 都要能匹配 |
| 中文路径（`微信开发者工具`、`图片`） | 全链路 UTF-8 无转码 |
| 目录名匹配 | 用 Unicode 归一化（`golang.org/x/text/unicode/norm`）处理全角/半角、繁简差异 |

## 6. 两阶段执行与 dry-run

### 6.1 强制流程

```
scan  →  scan.json  →  [人工审阅]  →  plan  →  plan.json  →  [人工审阅]  →  apply
```

**不允许跳过审阅**。`apply` 必须显式指定 plan 文件，且：

- `apply` **默认 dry-run**（只打印将要做什么），需要 `--yes` 才真正执行
- plan.json 里有 `scan_hash` 字段，`apply` 会校验 scan.json 未被改动（防止基于过时数据执行）
- plan.json 里的每个算子有 `enabled` 字段，用户可以手工改成 `false` 来跳过某项
- plan.json 是纯文本 JSON，可 diff、可版本控制、可发给别人复核

### 6.2 dry-run 的输出要求

dry-run 不是"少做一点"，而是**完整模拟**：
- 执行所有预检（真的去查空间、查占用、查权限）
- 计算预期回收量
- 输出每一步的确切动作（包括将执行的命令原文）
- 明确标注哪些步骤在 dry-run 下被跳过
- **不产生任何副作用**（包括不创建目标目录、不写 journal）

## 7. Journal 与可回滚性

### 7.1 写入时机

- **每个算子的每一步都写**，且 `fsync` 到磁盘，不能只在内存攒着
- 格式为 **JSONL**（每行一个 JournalEntry）—— 追加写，崩溃后已写入的行不会丢
- 位置：`%LOCALAPPDATA%\winclean\journal\<plan-id>.jsonl`

**为什么必须 fsync**：迁移 36 GB 的 VHDX 时断电是真实可能。如果 journal 只在内存里，重启后就不知道搬到哪一步了，也无法回滚。

### 7.2 崩溃恢复

`apply` 启动时若发现存在**未完成的 journal**（`FinishedAt == nil`），必须：

```
发现未完成的迁移操作：
  plan: abc123, 开始于 2026-09-14 11:30:00
  最后成功的步骤：seq 4 (复制 docker_data.vhdx 完成，校验通过)
  未完成的步骤：seq 5 (切换 Docker 指向) —— 状态 unknown

可能的状态：
  · 源数据完好，目标数据完好，Docker 仍指向源 → 可安全重试或回滚
  · 或者切换已部分完成

请选择：
  [r] 回滚到操作前状态
  [c] 尝试继续（若你确认切换未完成）
  [i] 忽略并保留现状（请手动检查 Docker 是否正常）
  [d] 查看详细日志
```

**绝不允许**在存在未完成 journal 时静默继续执行新操作。

### 7.3 不可回滚的情形必须提前说清

| 情形 | 可回滚性 |
| --- | --- |
| 环境变量、注册表、Known Folder、页面文件、休眠设置 | ✅ 完整回滚（只需改回配置） |
| Junction 迁移且源已清理 | ⚠️ 需把数据搬回，若空间不足则**不可回滚** |
| 删除的文件（未进回收站） | ❌ **不可回滚** |
| 删除的文件（进回收站） | ✅ 可从回收站恢复（除非超过容量被永久删除） |

**这些必须在 plan.json 与用户确认时明确标注**，不能等到出问题才说。

## 8. 归因缺口的诚实报告

本机实测有约 16 GB（回收站、卷影副本、根目录文件）因无管理员权限无法归因。**工具必须主动报告这个缺口，而不是假装数据完整。**

```
【归因覆盖率】84.1%   已归因 196.0 GB / 卷已用 233.1 GB
  ⚠️ 约 37 GB 未归因：
     · 约 16 GB  无权限读取（回收站、System Volume Information、其他用户 profile）
     · 约 21 GB  非目录类占用（pagefile.sys 24.3 GB 已单独统计，此处为其他根文件）
     以管理员权限运行可获得更完整结果
```

理由：如果用户看到「总占用 196 GB」但磁盘实际用了 233 GB，会怀疑工具不准，进而**不信任整个报告**——包括那些准确的部分。主动说明缺口反而增强可信度。

## 9. 日志与审计

| 项 | 要求 |
| --- | --- |
| 日志位置 | `%LOCALAPPDATA%\winclean\logs\winclean-YYYYMMDD.log` |
| 内容 | 不记录文件**内容**，只记录路径、大小、时间、操作类型 |
| 隐私 | 扫描结果含用户目录结构，**默认不上传任何数据**（NFR-8）。若未来做「规则建议提交」，必须显式让用户选择具体条目 |
| 保留 | 默认保留 7 天 |
| 敏感路径 | 对已知敏感路径（`.ssh`、`.aws`、凭据目录）在 DEBUG 日志中做路径脱敏，避免日志泄露 |
| 审计 | `apply` 的所有操作写入 journal（永久保留，由用户自行清理） |

### 10.1 测试环境的构造

| 需求 | 方式 |
| --- | --- |
| 需要 NTFS 才能建 Junction | `t.TempDir()` 在 NTFS 卷上即可（Windows 系统盘都是 NTFS） |
| 需要模拟"空间不足" | 用 `New-VHD` 创建小容量 VHD 并挂载，或用 quota |
| 需要模拟权限不足 | 用 `icacls` 构造拒绝访问的目录 |
| 需要模拟 Junction | `mklink /J`（不需提权） |

| 需要模拟 TOCTOU | 在扫描与执行之间用测试钩子替换目录 |
| 需要真实多样化路径 | 用 `12-实测基线与样例数据.md` 采集的脱敏目录树快照 |

## 11. 明确的安全红线（永不做）

| 红线 | 理由 |
| --- | --- |
| 永不删除 `C:\Windows\Installer` | 会导致软件无法卸载/修复/更新 |
| 永不删除 `WinSxS` | 会导致系统无法更新/修复 |
| 永不删除任何 `*.vhdx` / `*.vhd` | 是用户数据（镜像、容器、虚拟机） |
| 永不删除 Known Folder 下的文档类文件 | 用户创作内容 |
| 永不删除凭据类文件（`Login Data`、`.ssh`、证书） | 不可逆的身份信息丢失 |
| 永不建议删除用户数据 —— 只报告位置与大小 | 用户数据只能由用户自己或原软件迁移 |
| 永不跟随 reparse point 做递归删除 | 会越界删除 |
| 永不对 L0 路径提供"强制删除"选项 | 硬阻断不可绕过 |
| 永不在未完成 journal 的情况下继续执行 | 状态不可知 |
| 永不上传扫描数据 | 隐私 |
| 永不修改系统文件的所有权或 ACL 以"绕过"权限 | 这会引入严重的安全问题 |
| 永不批量删除"看起来是缓存"但未匹配规则的目录 | 「不知道 → 不删」 |
