## 1. 这个工具到底是什么

需求的原话是「Windows 垃圾清理」。但在对本机做实测侦察后（见 [`12-实测基线与样例数据.md`](./12-实测基线与样例数据.md)），结论是：**把目标定义成「垃圾清理」会做错方向。**

C 盘 237 GB，只剩 3.9 GB，已用 233 GB。这 233 GB 的构成：

| 占用项 | 大小 | 能不能「清理」 |
| --- | --- | --- |
| `%LOCALAPPDATA%\Docker\wsl\disk\docker_data.vhdx`（**单个文件**） | **36.0 GB** | ❌ 删了等于删掉所有镜像容器 → 应**迁移** + 压缩 VHDX |
| `pagefile.sys`（**单个文件**） | **24.3 GB** | ❌ 不能删 → 应**改到 D 盘** |
| `C:\Windows` | 22.3 GB | ❌ 系统，只有 WinSxS 外的零碎日志可清 |
| `C:\Program Files` + `(x86)` | 24.0 GB | ❌ 程序本体 |
| `hiberfil.sys`（**单个文件**） | **9.7 GB** | ❌ 不能删 → 应**关闭休眠功能** |
| `AppData\Local\JetBrains`（两版 IDE 索引，含已弃用的 2022.2） | 9.4 GB | ⚠️ 旧版本缓存可清，当前版本不可 |
| `AppData\Local\Yarn\Cache` | 8.2 GB | ⚠️ 可删（要重下）→ 更应**迁移** |
| `AppData\Roaming\Tencent`（微信/QQ 聊天与文件） | 6.9 GB | ❌ **用户数据**，应在本软件内迁移 |
| `AppData\Local\Android\Sdk` | 5.1 GB | ❌ SDK → 应**迁移** |
| `~\.cache`（puppeteer 2.7 + codex-runtimes 0.8 + …） | 3.5 GB | ⚠️ 可删（要重下）→ 更应**迁移** |
| `~\.m2\repository`（Maven 依赖） | 3.0 GB | ⚠️ 可删（要重下）→ 更应**迁移** |
| `AppData\Roaming\nvm`（多版本 Node） | 2.0 GB | ❌ 运行时 → 应**迁移** |
| `C:\ProgramData` | 6.6 GB | ❌ 程序公共数据 |
| 未归因（回收站/卷影/根文件，无管理员权限读不到） | ≈ 16 GB | — |
| `Temp` + 各家浏览器/编辑器 Cache + 更新包残留 | ≈ **2–3 GB** | ✅ **只有这一档才是「垃圾清理」** |

**结论很清楚**：传统口径下能安全删掉的只有 **2–3 GB**，对 `C:` 是杯水车薪。而真正的大头（Docker 36 GB、pagefile 24 GB、hiberfil 9.7 GB、各类缓存合计 20+ GB）**一个都不该删**——它们的正确出路是**迁移到 D 盘**（D 盘尚有 263 GB 空闲）或**调整系统设置**。

所以本工具的定位是：

> **磁盘空间归因 + 可清理性判定 + 可迁移性判定 三位一体。**
> 先回答「空间到底被什么占了」，再分别回答「哪些能删」和「哪些该搬」。
> **迁移与系统功能调整是主力，删除只是辅助。**

按本机数据估算，三类手段合计可回收 **≈ 100 GB**（迁移 ≈66 GB + 系统设置 ≈34 GB + 删除 ≈2–3 GB）。

一个佐证：本机 `JAVA_HOME=D:\workplace\jdk17`、`Maven_HOME=D:\workplace\apache-maven-3.9.6`、`D:\packages`、`D:\softw...`——**用户已经在手工往 D 盘搬东西了**。这个工具的本质是把这套手工流程自动化、批量化和可回滚化。

## 2. 四句话讲清设计

1. **一个扫描基础设施，三个分析器。** 目录遍历与大小统计只做一遍，产出被「空间归因」「可清理性判定」「可迁移性判定」三个分析器共享，最终合成一份 `scan.json`。
2. **可清理性分四级（L0 禁删 / L1 需确认 / L2 可安全清理 / L3 仅报告），默认只勾选 L2，且每条判定必须给出可读理由。** 核心原则是「不知道 → 不删」。
3. **迁移优先于删除。** 对 `Yarn\Cache`、`.m2`、`.cache`、`nvm`、`Android\Sdk` 这类「可删但要重下」的东西，正确动作是搬到 D 盘而不是删掉——所以 `migratability` 是一等公民，`plan.json` 里绝大多数算子应当是迁移算子。
4. **「调整系统设置」必须是一类正规算子。** 本机最容易拿回的两块是 `pagefile.sys` 24.3 GB（改到 D 盘）和 `hiberfil.sys` 9.7 GB（`powercfg /h off`，可逆）。这不是文件删除，而是 `ChangeSystemSetting` 算子，需要提权、需要可回滚、需要在报告里解释清楚取舍。

## 3. 本期范围（明确边界）

用户明确：**清理先不做，先做扫描。**

| 能力 | 本期 | 说明 |
| --- | --- | --- |
| 磁盘 / 目录扫描与大小统计 | ✅ 做 | M1 |
| 软件清单识别（装了什么、是干嘛的） | ✅ 做 | M2 |
| 软件下载/数据/缓存路径发现 | ✅ 做 | M3 |
| 可清理性分级判定（能删 / 不能删） | ✅ 做 | M4 |
| 虚拟磁盘（VHDX）识别与收缩建议 | ✅ 做 | M4（本机 36 GB 单项，不能被误判为垃圾） |
| 系统设置类建议（页面文件、休眠） | ✅ 做（**只出建议**） | M5 |
| 扫描报告输出（table / json / html） | ✅ 做 | M5 |
| 迁移方案生成（迁到哪、用哪种机制） | ✅ 做（**只出计划**） | M6 |
| 实际执行清理 | ❌ 不做 | M7，后续 |
| 实际执行迁移（复制/建链接/回滚） | ❌ 不做 | M7，后续 |
| 实际执行系统设置变更 | ❌ 不做 | M7，后续 |
| 重复文件查找、注册表清理、驱动更新 | ❌ 不做 | 非目标 |

## 5. 术语表

| 术语 | 含义 |
| --- | --- |
| **归因（Attribution）** | 把一个目录/文件的空间占用，归属到某个具体软件或系统组件的过程 |
| **Finding** | 扫描产生的一条「发现」，代表一个路径及其大小、类别、可清理等级与理由 |
| **L0 / L1 / L2 / L3** | 可清理性四个等级：禁删 / 需确认 / 可安全清理 / 仅报告。详见 `06` |
| **Known Folder** | Windows 的「已知文件夹」（下载、文档、图片…），可用 `SHGetKnownFolderPath` 查询，用户可重定向 |
| **Reparse Point** | NTFS 重解析点，包含符号链接、目录联接（Junction）、OneDrive 占位文件等。遍历时**必须识别且不跟随**，否则会越界删除 |
| **Junction（目录联接）** | NTFS 的目录级重定向。把目录搬到 D 盘后在原位置留一个联接，对软件完全透明。本工具迁移的主方案 |
| **规则库（Catalog）** | 内置的 YAML 知识库，描述「哪个软件是什么、有哪些路径、哪些能删、怎么迁」 |
| **Plan** | 由扫描结果生成的**变更计划**（要删什么 / 要迁什么），序列化为 JSON。执行阶段只读 Plan，不重新扫描 |
| **算子（Operator）** | 可执行的最小变更单元（如「删除目录 X」「把目录 X 迁到 Y 并建联接」） |
| **Journal** | 变更日志，记录每一步操作，用于回滚（undo） |
| **dry-run** | 只输出将要做什么，不做任何实际修改。本工具所有变更类命令**默认 dry-run** |

## 6. 十条核心设计决策（速览）

| # | 决策 | 一句话理由 |
| --- | --- | --- |
| 1 | 归因 / 可清理性 / 可迁移性是三个独立分析器，共享一次扫描 | 关注点分离，各自可独立测试与迭代 |
| 2 | 可清理性四级化，默认只勾 L2，每条必须可解释 | 清理工具的失败代价是数据丢失，保守优先 |
| 3 | 「不知道 → 不删」——未识别一律降级为 L1/L3 | 宁可少清，不可误删 |
| 4 | 规则库外置为 YAML 并 `embed` 进二进制 | 知识增长快于代码，规则要能独立演进 |
| 5 | 规则库必须覆盖**开发工具与 AI 工具缓存** | 实测 `.cache/puppeteer` 2.7 GB，传统清理软件完全扫不到 |
| 6 | 迁移主方案是 Junction，应用自身配置为辅 | Junction 适用面最广、不需软件配合、可回滚 |
| 7 | 迁移统一走「复制 → 校验 → 建链接 → 延迟删除」 | 绝不用 move，跨盘 move 中途失败会丢数据 |
| 8 | 扫描不需要管理员权限；清理/迁移才提权 | 降低使用门槛与心理负担，扫描可随时跑 |
| 9 | 两阶段执行：`scan` 出 `plan.json`，`apply` 只读 Plan | 计划可人工审阅、可 diff、可版本控制、可复现 |
| 10 | 遍历绝不跟随 reparse point，全链路 UTF-16 正确转换 | 防越界删除；本机存在中文路径（`OneDrive\图片`） |

## 7. 技术选型（已定）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | **Go 1.22+** | 单文件 exe、零运行时依赖、启动快、误报率低于 PyInstaller 打包 |
| Windows API | `golang.org/x/sys/windows` | 官方维护，直接 syscall |
| 注册表 | `golang.org/x/sys/windows/registry` | 同上 |
| CLI 框架 | `spf13/cobra` | 命令树清晰，子命令与 flag 规范 |
| 配置/规则库 | `gopkg.in/yaml.v3` + `embed` | 规则随二进制分发，无需外部文件 |
| 表格输出 | `olekukonko/tablewriter` | 终端可读性 |
| 并发编排 | 标准库 + `golang.org/x/sync/errgroup` | 够用，不引入重框架 |
| JSON | 标准库 `encoding/json` | 无外部依赖 |

UI 形态（后续 M8+）：优先 CLI，其次 **Wails**（Go 后端 + Web 前端，复用既有 Next.js/TS 技能，产出仍是单个 exe，依赖本机已有的 WebView2）。
