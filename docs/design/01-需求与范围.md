# 01 — 需求与范围

## 1. 背景

本机（Windows 11，详见 `12-实测基线与样例数据.md`）C 盘 237 GB 仅剩 3.9 GB，D 盘 931 GB 尚有 263 GB 空闲。用户已经在**手工**把开发环境往 D 盘搬（`D:\workplace\jdk17`、`D:\workplace\apache-maven-3.9.6`、`D:\packages`、`D:\softw...`），但手工搬的问题很明显：

- **不知道搬到哪、还剩什么没搬** —— 没有全局视图，全靠记忆和零散搜索。
- **不知道哪些能动、哪些不能动** —— 怕删坏系统或软件，导致不敢动，最后 C 盘继续满。
- **不知道空间到底被什么占了** —— Windows 自带的「存储设置」只到顶层目录粒度，看不到 `Roaming\Cursor` 里面哪部分是缓存、哪部分是配置和插件。
- **搬家过程不可回滚** —— 手工剪切粘贴，中途中断或搬错位置，软件就坏了。

本工具要把这套流程变成：**一次扫描 → 看清全局 → 得到可解释的删除建议与迁移计划 → （后续）一键执行且可回滚。**

## 3. 功能需求

### 3.1 扫描（本期核心）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 枚举本机所有固定磁盘（卷标、文件系统、总容量、剩余容量），排除光驱/网络盘/未挂载卷 | P0 |
| FR-2 | 遍历指定磁盘的目录树，统计每个目录的文件数与占用空间（逻辑大小与实际占用分别统计） | P0 |
| FR-3 | 遍历必须正确处理：长路径、无权限目录、中文/Unicode 路径、reparse point（**不跟随**）、硬链接（去重） | P0 |
| FR-4 | 支持 `--disk`、`--path`、`--exclude`、`--max-depth`、`--min-size` 过滤，支持快速模式与深度模式 | P1 |
| FR-5 | 扫描进度实时反馈；支持 Ctrl+C 优雅中断并输出已完成部分 | P1 |

### 3.2 软件识别（本期核心）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-10 | 从 HKLM(64/32) 与 HKCU 的 `Uninstall` 键读取已安装软件清单 | P0 |
| FR-11 | 读取 Microsoft Store / UWP 应用清单 | P1 |
| FR-12 | 识别便携/绿色软件（无注册表记录的目录型软件） | P2 |
| FR-13 | 识别游戏平台库（Steam `libraryfolders.vdf`、Epic manifest 等） | P2 |
| FR-14 | `InstallLocation` 缺失时，从 `UninstallString` / `DisplayIcon` 反推安装目录 | P0 |
| FR-15 | 多来源结果去重合并（按安装路径、再按「名称+发布者」） | P0 |
| FR-16 | 为每个软件给出「这是干什么的」（用途描述 + 分类），数据来自规则库 | P1 |
| FR-17 | 未识别的软件标记为 `unknown`，只参与空间归因，不参与清理判定 | P0 |

### 3.3 路径发现（本期核心）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-20 | 解析系统「已知文件夹」（下载、文档、图片、桌面、音乐、视频、AppData）的当前实际位置 | P0 |
| FR-21 | 解析用户级/系统级环境变量（`TEMP`、`NPM_CONFIG_CACHE`、`NVM_HOME`、`GRADLE_USER_HOME`、`PIP_CACHE_DIR`、`GOPATH`、`CARGO_HOME`、`HF_HOME` 等） | P0 |
| FR-22 | 通过规则库发现各软件的缓存/数据/下载/配置目录（含变量模板，如 `%LOCALAPPDATA%\Google\Chrome\User Data`） | P0 |
| FR-23 | 启发式发现：遍历 `%LOCALAPPDATA%`/`%APPDATA%`/`%ProgramData%` 一级子目录，匹配 `Cache`/`GPUCache`/`Code Cache`/`logs`/`CrashDumps`/`tmp` 等命名模式，**给出置信度** | P1 |
| FR-24 | 检测 OneDrive 接管「桌面/文档/图片」的情况并显式告警 | P0 |
| FR-25 | 把发现的路径归因到具体软件（owner），无法归因的挂到 `system` 或 `unknown` | P0 |

| 编号 | 需求 | 优先级 |

| FR-43 | 计划可序列化为 JSON 并人工审阅、修改 | P0 |

### 3.5.1 虚拟磁盘（VHDX）专项

本机实测 `docker_data.vhdx` 36.0 GB，是 C 盘最大单项，且**极易被误判为可删**（"一个缓存文件"）。必须专门处理：

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-45 | 识别所有 `*.vhdx` / `*.vhd` 文件（不限于 Docker：WSL2 发行版、Hyper-V、Windows Sandbox） | P0 |
| FR-46 | 一律判为 L3（仅报告）+ 强制迁移建议，**任何情况下不得建议删除** | P0 |
| FR-47 | 报告「逻辑大小 vs 实际占用」差异，并提示动态扩展 VHDX 存在内部空洞 | P0 |
| FR-48 | 给出收缩建议（`docker system prune` + `Optimize-VHD` / `diskpart compact vdisk`），并说明预期回收量 | P1 |
| FR-49 | 识别 VHDX 归属（Docker Desktop / WSL 发行版名 / Hyper-V 虚拟机名） | P1 |

### 3.5.2 系统设置调整（非文件操作）

这是本机第二、三大回收项（`pagefile.sys` 24.3 GB、`hiberfil.sys` 9.7 GB），**不是删除而是改设置**。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-55 | 识别并报告 `pagefile.sys` / `hiberfil.sys` / `swapfile.sys` 的实际大小与当前配置 | P0 |
| FR-56 | 生成 `ChangeSystemSetting` 建议：页面文件移到其他盘、关闭休眠 | P0 |
| FR-57 | 每条建议必须说明：可回收容量、所需权限、副作用、**可逆性及回滚方式** | P0 |
| FR-58 | 页面文件建议必须覆盖「C 盘保留小分页文件用于崩溃转储」这一取舍，不能简单建议完全移走 | P0 |
| FR-59 | 实际执行这些设置变更 | **本期不做**（同 M7） |

## 4. 非功能需求

| 编号 | 需求 | 指标 |
| --- | --- | --- |
| NFR-1 | 扫描速度 | 本机 C 盘（约 50–80 万文件）快速模式 ≤ 30 秒；深度模式 ≤ 3 分钟 |

| NFR-6 | 可回滚性 | 所有变更以算子 + journal 形式组织，为 M7 的回滚能力预留（本期只定义数据结构） |
| NFR-7 | 可移植性 | Windows 10 1809+ / Windows 11，amd64 优先；arm64 后续 |
| NFR-8 | 离线可用 | 不依赖网络。规则库随二进制分发 |

## 5. 非目标（明确不做）

| 不做 | 原因 |
| --- | --- |
| 本期不做任何实际删除 | 用户明确「清理先不做」；且先做扫描能让规则在真实数据上被反复验证 |
| 本期不做实际迁移执行 | 同上，先出计划 |
| 注册表清理 | 收益极低、风险极高，且几乎不释放空间 |
| 驱动更新 / 系统优化 / 启动项管理 | 与「空间治理」目标无关，是另一个产品 |
| 杀毒 / 恶意软件扫描 | 非本工具职责 |
| 重复文件查找 | 有价值但独立，后续单独设计（`--dedup` 子命令） |
| 清理 `WinSxS` / `C:\Windows\Installer` | **永久禁止**。前者需 `DISM` 且收益被夸大，后者删除会导致软件无法卸载/修复 |
| 自动上传扫描结果到云端 | 隐私红线 |
| 跨平台（macOS/Linux） | 规则库与 API 都强绑定 Windows，不做虚假的可移植性 |

## 6. 约束

| 约束 | 影响 |
| --- | --- |
| 需在 Windows 上开发调试 | 无法用 Linux CI 跑集成测试；考虑用 GitHub Actions 的 `windows-latest` |
| HKLM 读取与所有写操作需要权限差异 | 实现时必须在无管理员权限下也能完成扫描主体（HKLM 只读通常允许普通用户；写操作一律提权） |
| 杀毒软件可能拦截 | 避免危险 API 组合（如递归删除 + 隐藏窗口），行为要可解释 |
| 路径编码 | 全链路 UTF-16 ↔ UTF-8 正确转换，绝不走 ANSI 代码页（本机已实测到 `图片` 在 GBK 控制台下乱码为 `ͼƬ`） |
| 长路径 | 必须使用 `\\?\` 前缀，否则超过 260 字符的路径会失败 |

## 7. 架构决策记录（ADR）

| # | 决策 | 备选 | 理由 |
| --- | --- | --- | --- |
| ADR-1 | 用 Go 实现 | Python / Java / C# / Rust | 单 exe 零依赖、体积小启动快、杀软误报低。用户已确认 |
| ADR-2 | 本期只做扫描，清理/迁移执行延后 | 一次做完 | 清理规则必须在真实数据上验证过才敢执行；先扫描可零风险迭代 |
| ADR-3 | 三分析器共享一次扫描 | 三个独立工具 | 目录遍历是 O(文件数) 的重操作，重复遍历不可接受 |
| ADR-4 | 可清理性四级（L0–L3）而非黑白名单 | 二元白/黑名单 | 灰区太多（Prefetch、Downloads、包管理器缓存、聊天记录），二元模型会迫使做出危险简化 |
| ADR-5 | 规则库外置 YAML 而非硬编码 | Go 代码内硬编码 | 知识增长快于代码；YAML 便于 review 与贡献；schema 可校验 |
| ADR-6 | 迁移主方案 Junction | 直接改各软件配置 | Junction 对软件透明、适用面最广、可回滚；改应用配置需逐软件适配且未必支持 |
| ADR-7 | 迁移路径统一走 copy→verify→link→删 | 直接 move | 跨盘 move 非原子，中途失败会丢数据；copy 失败可安全重试 |
| ADR-8 | `scan` 与 `apply` 分离，中间用 `plan.json` | 扫描完直接执行 | 计划可审阅、可 diff、可复现、可交给他人复核 |
| ADR-9 | 遍历不跟随 reparse point | 跟随 | OneDrive 占位文件与 Junction 会造成重复计数甚至越界操作 |
| ADR-10 | 仅 CLI，UI 后续用 Wails | 起步就做 GUI | 先跑通判定逻辑与规则库；本机已有 WebView2，Wails 后续可平滑加 |

## 8. 成功判据

工具做完 M6 时，必须能在这台机器上产出如下结论并**经人工复核全部正确**：

1. **归因准确**：明确列出占用 C 盘 233 GB 的前 10 大项，且归因正确。必须包含 `docker_data.vhdx` 36.0 GB、`pagefile.sys` 24.3 GB、`hiberfil.sys` 9.7 GB、`JetBrains` 9.4 GB、`Yarn\Cache` 8.2 GB。
2. **识别 VHDX**：把 `docker_data.vhdx` 判为 L3（仅报告）+ 迁移建议，并提示「动态扩展，可用 `docker system prune` + `Optimize-VHD` 收缩」，**绝不能标为可删除**。
3. **识别系统可回收项**：给出 `pagefile.sys` → 改到 D 盘、`hiberfil.sys` → `powercfg /h off` 两条 `ChangeSystemSetting` 建议，含容量、前提（提权）、副作用、可逆性说明。
