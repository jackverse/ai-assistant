# 20 — 扩展模块架构规范

> 状态：**生效中（硬性规则）** · 2026-09-15
> 需求原话：「这个项目就算塞了 100 个甚至更多的功能，只要没有用到，就不要加载进来，
> 所以每个模块都应该是类似扩展模块那种概念集成进来的，不加载就不造成运行负担。」
> 操作版（每次开发都要对照的清单）见仓库根目录 [`AGENTS.md`](../../AGENTS.md)。

---

## 1. 这条规则要解决的真问题

本工具已经经历过一次「功能变多 → 入口变重」的早期征兆：

- `disk` 模块把**扫描 / 清理 / 迁移**三件事塞进一个模块 id，三块状态全挂在 `App` 上；
- `internal/javadev` 已经写完（服务启停、依赖加载、Git 变更），但**没注册进模块注册表**，
  前端也零引用——等于「写好了但进不去」；
- `javadev_api.go` 用包级 `var devMgr = javadev.NewManager()` 持有模块运行时。

这些都不是 bug，但放任下去的结果就是：**功能数 ↑ ⇒ 启动与常驻开销 ↑**，
最后没人敢加功能。本规范把「不加载就不造成运行负担」从口号变成一条**可证伪**的工程约束：

> **把一个功能模块的代码整体摘掉，程序的行为与启动耗时不应有任何可观察差别**
> ——除非你恰好进入那个页面。

「可证伪」是关键：任何无法被测量的说法（「我们做了懒加载」）都不算合规。

---

## 2. 三条不变式

| # | 不变式 | 落地位置 |
| --- | --- | --- |
| 1 | **功能是模块，不是页面片段。** 新增功能 = 新增一个模块 id + 一份 `Meta` + 一个 `OpenFn`；不接受向既有模块内塞页签。 | `app.go` → `registerModules()` |
| 2 | **主页是配置，不是写死。** `general.home` 指向恰好一个已启用模块；其余已启用模块作为扩展页出现在导航。 | `internal/config` → `General.Home` |
| 3 | **禁用 = 消失，启用 ≠ 加载。** `modules.<id>.enabled=false` 时导航不出现、后端拒绝进入、其代码零执行；即使启用，**也要等用户真正进入页面**才初始化。 | `modules.Registry.Open` / `config.IsEnabled` |

不变式 3 的后半句最容易做错：很多实现把「启用」当成「初始化」。
在本项目里，`enable` 只影响**可见性与可进入性**，
`SetEnabled` 明确不会触发 `OpenFn`（见 `internal/modules/modules.go`）。

## 3. 模块解剖

一个模块由四块组成，缺一不可：

```
internal/<id>/           ① 纯逻辑包：业务实现 + 单测
                         不 import wails、不 import main、不碰全局状态
<id>_api.go              ② 绑定层（main 包）：App 上的方法 + DTO
                         类型必须定义在 main 包（原因见 §6）
app.go registerModules() ③ 注册：Meta + OpenFn（懒加载钩子）
frontend/dist/index.html ④ 页面：<section id="page-<id>"> + init<Id>() + PAGE_META
```

**命名**：模块 id 为单数小写单词（`chat` / `disk` / `deploy` / `javadev`），
它就是配置键（`modules.<id>.enabled`）、前端 DOM id（`page-<id>`）、
`OpenFn` 的调用标识——**同一个字符串在四个位置出现，不允许不一致**。

## 4. 生命周期：每个阶段允许发生什么

```
            注册表构造            用户点进页面              用户离开 / 禁用
   ┌──────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
   │ 已注册    │ → │ 启用但未进入  │ → │ 已进入(opened)│ → │ 禁用          │
   │ 元数据而已│   │ 零执行        │   │ 模块自己负责  │   │ 回到零执行    │
   └──────────┘   └──────────────┘   └──────────────┘   └──────────────┘
    只有字符串       OpenFn 未调用      显式动作才干活      opened 重置，
    与函数值         无 IO/无 goroutine                   重进重新懒加载
```

| 阶段 | 允许 | 禁止 |
| --- | --- | --- |
| 已注册 | 声明 `Meta`、提供 `OpenFn` 函数值 | 在注册时做任何 IO、探测、建连接、起协程 |
| 启用未进入 | 在前端导航里出现、可被点击 | `OpenFn` 被调用；后端为该模块分配资源 |
| 已进入 | `OpenFn` 的毫秒级初始化；用户显式动作触发的重活（扫描、构建、启停服务） | 用户没点击就自动开始跑的重活 |
| 禁用 | 导航移除、`EnterModule` 返回可读拒绝原因 | 残留订阅、定时器、子进程、文件句柄 |

`Registry.Open` 的三条拒绝路径都必须给出**可读原因**（未知模块 / 被禁用 / 未开发完），
这是「用户需要知道功能存在但被我关了」的同一个原则的延续。

## 5. 懒加载预算：`OpenFn` 里能写什么

`OpenFn` 是唯一的懒加载钩子，判断标准是**「用户点一下，能忍受多久」**：目标 < 10 ms。

| 可以做 | 不可以做（必须推迟到用户显式动作） |
| --- | --- |
| 读该模块自己的配置/规则文件（KB 级） | 遍历文件系统、统计目录大小 |
| 校验该模块是否可用，给出提示文案 | 枚举磁盘、读注册表全表 |
| 绑事件、注册回调 | 探测工具链（JDK/Maven）、扫端口 |
| 返回「就绪」提示 | 发起任何 HTTP 请求、启动子进程 |

现成的两个正例都在 `app.go` 的 `registerModules()` 里：
`chat` 的 `OpenFn` 不建连接、不探测网络；`deploy` 的 `OpenFn` 不探测工具链，
探测由页面上「重新探测」触发。新模块照这个尺度写。

## 6. 两个必须知道的坑

### 6.1 Wails 会静默丢弃引用 `internal/...` 类型的绑定方法

实测（本机 GUI 验证）：`App` 上签名直接引用 `internal/modules` 包类型的绑定方法
**不会出现在前端**，且没有任何报错。因此模块对前端暴露的 DTO 一律定义在 `main` 包
（`ModuleDTO`、`OpenModuleResult` 就是这个原因，见 `app.go:211` 注释）。
新增模块绑定方法时，若前端 `A().Xxx` 报未定义，先查这条。

### 6.2 包级 `var` 是隐式 `init`

`var devMgr = javadev.NewManager()` 这类写法在**任何**代码路径导入该包时执行。
当前 `NewManager` 只建了一个空 map，成本可忽略；但这是错误示范——
一旦有人给 `NewManager` 加上「恢复上次的服务实例」这种逻辑，入口就悄悄变重了。
新增模块的运行时对象应当由 `OpenFn` 或首次使用的 `sync.Once` 创建。

## 7. 合规自检（提交前）

```bash
make test && make vet          # 回归
make gui                       # 构建桌面版，观察标题旁「启动 X ms」
```

四项人工验证，缺一不可：

1. **启动耗时**：加模块前后 `启动 X ms` 差值在噪声内。
2. **零副作用**：只启动、不进入该模块页 → 该模块无日志、无网络请求、无子进程、无文件遍历。
3. **可禁用**：`modules.<id>.enabled: false` → 导航无此页、`EnterModule` 被拒且原因可读、其余功能正常。
4. **可摘除**：注释掉该模块的注册与前端页面，程序仍能编译运行——做不到说明耦合泄漏了。

前两项可以靠 [`internal/modules/lazy_test.go`](../../internal/modules/lazy_test.go)
的自动化断言兜住（断言「未 `Open` 的模块，其 `OpenFn` 未被调用」）。

## 8. 现存欠账与改造顺序

**改造原则**：一次一个模块；改完按 §7 验收；不为「一次性对齐规则」做破坏安全边界的大重构
（清理/迁移路径的安全约束优先级高于本规范）。

| 顺序 | 对象 | 现状 | 目标 |
| --- | --- | --- | --- |
| 1 | `javadev` | 代码已写完，未注册、前端零引用 | 补注册 + 补 `page-javadev`，让功能真正可达；`devMgr` 移出包级 `var` |
| 2 | `disk` 三合一 | 扫描/清理/迁移共用一个模块 id 与 `App` 状态 | 拆为 `scan` / `clean` / `migrate` 三个模块，各自可禁用；共用配置归属先定清楚 |
| 3 | 配置归属 | `deploy` 与 `javadev` 共用 `deploy` 段配置 | 明确「项目清单」属于谁；避免一个模块禁用后另一个读不到配置 |
| 4 | 前端页面 | 单文件 `index.html` 持续变大 | 页面按模块切成独立文件（当前无构建工具链，需先定方案再动） |

第 2 项完成后，[`14-主副页面与AI集成设计.md`](./14-主副页面与AI集成设计.md) §1 里画的三块扩展页
（扫描/清理/迁移）才算与注册表一致——目前文档比实现更「合规」，这是要修的方向，不是实现要向文档妥协。
