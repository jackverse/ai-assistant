# 05 — 路径发现

回答「软件的下载、数据、缓存分别放在哪」。这是**路径迁移功能的前提**——不知道现在在哪，就谈不上搬去哪。

---

## 1. 为什么不能只靠「规则库硬编码路径」

直觉做法是给每个软件写死路径清单。但这条路走不通：

1. **路径是用户可配置的**。本机 `JAVA_HOME=D:\workplace\jdk17`、`Maven_HOME=D:\workplace\apache-maven-3.9.6` 就是活例子——用户已经把东西搬走了，硬编码的 `C:\...` 会指向不存在的路径。
2. **Known Folder 可被重定向且已被重定向**。本机实测 `Desktop` → `C:\Users\33380\OneDrive\Desktop`、`Pictures` → `C:\Users\33380\OneDrive\图片`，但 `Downloads` 仍在 `C:\Users\33380\Downloads`。硬编码 `%USERPROFILE%\Desktop` 是错的。
3. **软件的路径模板里含变量**，变量的值本身是动态的（`%LOCALAPPDATA%` 因用户而异）。

所以正确做法是：**规则库只声明「相对于哪些根、用什么模式」，实际的根在运行时解析。**

## 2. 五条发现路径

```
  ┌─────────────────────────────────────────────────────────────────┐
  │ ① Known Folder 解析（系统已知文件夹的实际位置）                      │
  │    SHGetKnownFolderPath + 注册表 User Shell Folders              │
  ├─────────────────────────────────────────────────────────────────┤
  │ ② 环境变量解析（用户级 / 系统级 / 进程级）                            │
  ├─────────────────────────────────────────────────────────────────┤
  │ ③ 注册表指向（Explorer 配置、软件自定义键）                           │
  ├─────────────────────────────────────────────────────────────────┤
  │ ④ 规则库模板展开（%LOCALAPPDATA%\Google\Chrome\User Data）         │
  ├─────────────────────────────────────────────────────────────────┤
  │ ⑤ 启发式发现（遍历 AppData/* 一级子目录，按命名模式 + 置信度）          │
  └─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                   统一进入 PathCandidate 池
                   → 存在性校验 → 去重 → 归因（owner）→ PathKind 分类
```

## 3. ① Known Folder 解析

### 3.1 两种来源，都要用，且用途不同

| 来源 | 给出什么 | 用途 |
| --- | --- | --- |
| `SHGetKnownFolderPath(FOLDERID_*)` | **当前实际位置**（已展开、已解析重定向） | 定位真实目录 |
| `HKCU\...\Explorer\User Shell Folders` | **原始模板值**，可能含 `%USERPROFILE%` | 判断「是否被重定向过」、为迁移**写入新值**用 |

**必须两个都读**。只读 API 无法知道「用户是否改过」，只读注册表可能拿到未展开的变量且不反映某些系统级重定向。

### 3.2 需要解析的 Known Folder 清单

| FOLDERID | 中文 | 迁移价值 |
| --- | --- | --- |
| `FOLDERID_Downloads` | 下载 | **★★★ 最高**——最该重定向到 D 盘 |
| `FOLDERID_Documents` | 文档 | ★★ 风险高（见 §3.4） |
| `FOLDERID_Desktop` | 桌面 | ★★ 本机已被 OneDrive 接管 |
| `FOLDERID_Pictures` | 图片 | ★★ 本机已被 OneDrive 接管 |
| `FOLDERID_Music` | 音乐 | ★ |
| `FOLDERID_Videos` | 视频 | ★ |
| `FOLDERID_LocalAppData` | `%LOCALAPPDATA%` | 解析用（不迁移） |
| `FOLDERID_RoamingAppData` | `%APPDATA%` | 解析用（不迁移） |
| `FOLDERID_ProgramData` | `%ProgramData%` | 解析用 |
| `FOLDERID_ProgramFiles` / `X86` | 程序目录 | 解析用 |
| `FOLDERID_Templates` | 模板 | — |
| `FOLDERID_Profile` | 用户根 | 解析用 |
| `FOLDERID_PublicDocuments` etc. | 公共目录 | — |

### 3.3 本机实测结果（这就是「为什么必须读实际值」的证据）

| 项 | User Shell Folders（原始） | 实际值 |
| --- | --- | --- |
| Desktop | `C:\Users\33380\OneDrive\Desktop` | 同 |
| Personal (文档) | `C:\Users\33380\Documents` | 同 |
| My Pictures | `C:\Users\33380\OneDrive\图片` | 同 |
| My Music | `C:\Users\33380\Music` | 同 |
| My Video | `C:\Users\33380\Videos` | 同 |
| **`{374DE290-...}`（下载）** | **`C:\Users\33380\Downloads`** | 同，**未重定向** |
| Local AppData | `C:\Users\33380\AppData\Local` | 同 |
| AppData | `C:\Users\33380\AppData\Roaming` | 同 |

**两个可直接落地的结论**：
1. **下载目录是首选重定向目标**——仍在 C 盘、未被接管、重定向风险最低。
2. **桌面/图片已被 OneDrive 接管**——工具必须**识别并告警，默认不参与迁移**（把它重定向走会破坏 OneDrive 同步）。

### 3.4 OneDrive 接管检测（FR-24）

```go
func detectOneDriveTakeover(kf KnownFolder) (bool, string) {
    p := kf.ActualPath
    // 判据 1：路径出现在任何 OneDrive 根下
    for _, od := range oneDriveRoots() {   // 从 %OneDrive% / %OneDriveConsumer% / %OneDriveCommercial% 拿
        if hasPathPrefix(p, od) { return true, "路径位于 OneDrive 根下: " + od }
    }
    // 判据 2：KnownFolder 的 reparse point 指向 OneDrive
    if tag, target := readReparse(p); isReparse(tag) && containsFold(target, "OneDrive") {
        return true, "目录是 OneDrive 联接: " + target
    }
    // 判据 3：存在 OneDrive 的同步标记文件
    if exists(filepath.Join(p, "desktop.ini")) && containsFold(readIni(p), "OneDrive") {
        return true, "存在 OneDrive desktop.ini 标记"
    }
    return false, ""
}
```

检测到接管的目录：
- 在报告中显式标注「由 OneDrive 管理」
- **迁移判定直接跳过**（机制无法适用，强行改会破坏同步）
- 在扫描结果中把它的空间占用标注为「云端占位可能未下载」，避免虚报

## 4. ② 环境变量解析

### 4.1 三个作用域

| 作用域 | 读取方式 | 特点 |
| --- | --- | --- |
| 进程级 | `os.Getenv` / `os.Environ` | 最准（当前进程实际生效的值） |
| 用户级 | `HKCU\Environment` | 迁移时**写这里**；改动对已运行进程无效 |
| 系统级 | `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment` | 需管理员写 |

**读取顺序**：进程级 > 用户级 > 系统级。判断「当前值是否等于注册表值」可检测出「改了但没重启/没广播」。

### 4.2 迁移相关的环境变量清单（规则库维护）

| 变量 | 对应软件/工具 | 本机实测值 | 迁移价值 |
| --- | --- | --- | --- |
| `TEMP` / `TMP` | 系统临时目录 | `C:\Users\33380\AppData\Local\Temp` | ★★ |
| `NVM_HOME` | nvm（多版本 Node） | `C:\Users\33380\AppData\Roaming\nvm`（**2.0 GB**） | ★★★ |
| `NVM_SYMLINK` | nvm 的 node 软链 | `C:\Program Files\nodejs` | 不应改（需管理员且是链接） |
| `JAVA_HOME` | JDK | `D:\workplace\jdk17` | 已迁 |
| `Maven_HOME` | Maven | `D:\workplace\apache-maven-3.9.6` | 已迁 |
| `MAVEN_OPTS` / `settings.xml` 的 `localRepository` | Maven 本地仓库 | 未显式设置 → 默认 `~/.m2/repository`（**3.0 GB**） | ★★★ |
| `PIP_CACHE_DIR` | pip 缓存 | 未设置 → 默认 `%LOCALAPPDATA%\pip\Cache`（**305 MB**） | ★★★ |
| `NPM_CONFIG_CACHE` | npm 缓存 | 未设置 → 默认 `%LOCALAPPDATA%\npm-cache`（**304 MB**） | ★★ |
| `GRADLE_USER_HOME` | Gradle | 未设置 → 默认 `~/.gradle`（本机不存在） | ★★ |
| `GOPATH` / `GOCACHE` | Go | 未设置，Go 未安装 | ★★ |
| `CARGO_HOME` | Rust | 未设置 | ★ |
| `CONDA_PKGS_DIRS` | Conda | 未设置 | ★★ |
| `HF_HOME` / `TRANSFORMERS_CACHE` | HuggingFace 模型 | 未设置 | ★★★（模型动辄几十 GB） |
| `TORCH_HOME` | PyTorch | 未设置 | ★★ |
| `DOCKER_DATA_ROOT`（是 daemon 配置不是环境变量） | Docker | 未安装 | ★★★（`ext4.vhdx` 极大） |

> **注意 `NVM_HOME` 这一项**：本机 nvm 目录 2.0 GB，里面是多个 Node 版本（实测存在 `v10.15.3`、`v11.0.0` 等）。这是**典型的高价值低风险迁移目标**——只要改 `NVM_HOME` 并把目录搬过去即可，nvm 完全支持。

### 4.3 变量模板展开器

规则库里的路径模板需要在运行时展开：

```
支持语法：
  %VAR%                 → 环境变量（不区分大小写，Windows 惯例）
  ${VAR}                → 同上，更明确，推荐在规则库中使用
  {FOLDERID_Downloads}  → Known Folder 引用（用花括号 + 已知 ID）
  {UserProfile}         → 内置变量：当前用户根
  {SystemDrive}         → 内置变量：系统盘符（通常是 C:）
  {UserDocs} 等         → 内置变量别名

约束：
  - 展开后必须是绝对路径
  - 展开后必须做 Clean + 转义校验（防注入 ../../）
  - 展开失败（变量不存在）→ 标记该候选路径 Unresolved，不参与判定
  - 变量值本身含中文/空格 → 原样保留，不做任何转码（本机已实测到 GBK 乱码坑）
```

**实现要点**：不要用 `os.ExpandEnv`。它只认 `$VAR`/`${VAR}`，且会**静默把未定义的变量替换成空串**——这会生成 `\Google\Chrome` 这样的相对路径，进而可能被误解析为当前目录下的路径，是安全隐患。必须自己实现，未定义变量要显式报错。

## 5. ③ 注册表指向

部分软件把路径存在自己的注册表键里。规则库可声明：

```yaml
paths:
  - kind: data
    registry: HKCU\Software\Tencent\WeChat
    value: FileSavePath          # 微信的文件保存位置
    default: "%USERPROFILE%\Documents\WeChat Files"
```

需要覆盖的常见位置：

| 软件 | 键 / 值 |
| --- | --- |
| 微信 | `HKCU\Software\Tencent\WeChat\FileSavePath` |
| QQ | `HKCU\Software\Tencent\QQ\...` |
| 各类 Electron 应用 | 多数不存注册表，用 `%APPDATA%` 约定 |
| Docker Desktop | `%APPDATA%\Docker\settings-store.json`（JSON 配置，非注册表） |
| Steam | `HKCU\Software\Valve\Steam\SteamPath` |
| 浏览器 | 一般无（默认 profile 路径固定） |

**注意**：注册表指向的值**可能为空或不存在**（用户从未改过设置），此时回退到 `default`。

## 6. ④ 规则库模板展开

这是发现量的主力。规则库为每个软件声明「可能有哪些路径」：

```yaml
id: google.chrome
paths:
  - kind: data
    template: "%LOCALAPPDATA%\\Google\\Chrome\\User Data"
    note: "浏览器用户数据（配置、书签、Cookie、历史）"
    cleanable_level: L1        # 整体不可删
  - kind: cache
    template: "%LOCALAPPDATA%\\Google\\Chrome\\User Data\\{Profile}\\Cache"
    glob_profile: true         # {Profile} 展开为 Default / Profile 1 / ...
    cleanable_level: L2        # 缓存可删
  - kind: cache
    template: "%LOCALAPPDATA%\\Google\\Chrome\\User Data\\{Profile}\\Code Cache"
    glob_profile: true
    cleanable_level: L2
  - kind: cache
    template: "%LOCALAPPDATA%\\Google\\Chrome\\User Data\\{Profile}\\GPUCache"
    glob_profile: true
    cleanable_level: L2
  - kind: config
    template: "%LOCALAPPDATA%\\Google\\Chrome\\User Data\\{Profile}\\Login Data"
    cleanable_level: L0        # 密码库，绝对禁删
  - kind: config
    template: "%LOCALAPPDATA%\\Google\\Chrome\\User Data\\{Profile}\\Bookmarks"
    cleanable_level: L0        # 书签
```

**关键设计点**：注意上面的模式——**同一个「用户数据」根下，`Cache` 是 L2 可删，`Login Data`/`Bookmarks` 是 L0 禁删**。这正是为什么 `cleanability` 必须做到**子路径级精细判定**，而不能只给顶层目录定级。如果只报「Chrome 用户数据 1.2 GB，不可删」，用户就永远清不出空间；如果粗放地说「Chrome 目录可删」，用户会丢密码和书签。

### 6.1 Profile 通配

Chromium 系（Chrome/Edge/零信浏览器/Brave）和 Firefox 都有多 profile 结构。规则库用 `glob_profile: true` 声明，引擎展开为实际存在的 profile 目录：

```
User Data/
├── Default/            ← 默认 profile
├── Profile 1/          ← 附加 profile
├── Profile 2/
├── System Profile/     ← 系统 profile（特殊处理）
├── Guest Profile/
├── Local State         ← 文件，含 profile 索引
└── ...
```

展开时优先读 `Local State`（JSON）里的 `profile.info_cache` 拿到准确的 profile 列表，失败再退化为目录名模式匹配。

1. **「更新包残留」自成一类**：`@mmx-agentelectron-updater`(729 MB) + `Docker Desktop Installer`(591 MB) + `termius-updater`(498 MB) = **1.8 GB**，全是可安全删除的安装/更新包残留。规则库需要 `*-updater`、`* Installer`、`*Setup*`、`* Installer *` 等命名模式专门建模。
2. **「浏览器二进制缓存重复下载」**：`puppeteer`(2.7 GB) + `ms-playwright`(0.74 GB) + `Cypress`(0.63 GB) + `chrome-devtools-mcp`(143 MB) = **4.2 GB**，四个工具各自下载了一份 Chromium。规则库应把这类归为一组，并在报告中给出「可复用同一份 Chromium」的洞察。
3. **`vhd` 必须是一等 PathKind**：`docker_data.vhdx` 36 GB 是 C 盘最大单项，如果它落进 `unknown` 或被误判为 `cache`，后果是灾难性的。

**⚠️ npm 缓存有两个位置**：本机同时存在 `%LOCALAPPDATA%\npm-cache`（304 MB）与 `%APPDATA%\npm-cache`（1.0 GB）。这是 npm 版本变更导致的历史遗留。设计含义：**同一 `PathKind` 可能有多个候选位置，必须全部枚举，不能只取第一个命中的**。同时这类「同一软件同类路径出现多处」本身就是值得报告的信息。

**未识别路径（如 `secoresdk`）**：必须能被报告为「未知目录，占 0.86 GB，请人工确认」。这是启发式发现的价值——即使规则库不覆盖，用户也能看到它。

## 7. ⑤ 启发式发现（FR-23）

### 7.1 扫描范围

固定扫这些根的一级（或两级）子目录：

```
%LOCALAPPDATA%\*           (约 150 项)
%APPDATA%\*                (约 120 项)
%LOCALAPPDATA%\Programs\*  (per-user 便携软件)
%ProgramData%\*
%USERPROFILE%\.cache\*
%USERPROFILE%\.*\          (点目录：.gradle/.m2/.cargo/.conda/.npm/.pnpm-store/.nuget)
```

| `tmp` / `temp` / `.tmp` | temp | 0.8 | |
| `IndexedDB` | data | 0.5 | **是数据不是缓存**，可能含离线数据 |

| `blob_storage` / `File System` | data | 0.5 | |
| `Crashpad` / `Crash Reports` | dump | 0.9 | |
| `.cache` | cache | 0.85 | |
| `ShaderCache` | cache | 0.95 | |
| `Downloaded Installations` / `Installer` / `Updates` | cache | 0.6 | 更新包，通常可删 |
| `node_modules` | data | 0.3 | **绝不可自动删**，只是归因用 |

### 7.3 置信度如何影响判定（重要）

启发式结果**永远不能单独把路径提升到 L2**，除非置信度 ≥ 0.9 **且** 该路径位于一个已知的缓存类父目录下。规则：

```
if 命中规则库:
    使用规则库声明的 level          ← 权威
elif 启发式置信度 >= 0.9 且 父目录属于已知软件的数据目录:
    L2（可安全清理）                ← 高置信启发式可判 L2
elif 启发式置信度 >= 0.7:
    L1（需确认）                    ← 中等置信度只敢判 L1
else:
    L3（仅报告）                    ← 低置信度只报告
```

这条规则是对「不知道 → 不删」原则的具体化：**启发式的置信度直接决定它能推动的判定上限**。

### 7.4 未识别目录也必须上报

启发式的另一半价值不在「认出了什么」，而在**「没认出什么」**。本机 `%APPDATA%\secoresdk` 占 0.86 GB，规则库不认识。报告必须能显示：

```
[未知] 0.86 GB  %APPDATA%\secoresdk
       未匹配任何规则，无法判定安全性。可通过 `winclean dir "<path>"` 查看构成，
       或提交规则建议。
```

## 8. 归因（owner 判定）

路径发现完之后，每个路径都要归属到某个 App（或 `system`）。按优先级：

```
1. 规则库显式声明（template 属于某个 AppRule）→ owner = 该 App，置信度 1.0
2. 路径位于某 App 的 InstallLocation 之下 → owner = 该 App，置信度 1.0
3. 路径的父目录名与某 App 的 DisplayName/alias 匹配（归一化后）→ 置信度 0.7
4. 路径名与规则库的 dir_patterns 匹配（如 `Tencent` 目录 → 腾讯系）→ 置信度 0.6
5. 环境的进程/文件特征（如目录下有 `<name>.exe`）→ 置信度 0.8
6. 无法归因 → owner = "unknown"，并在报告中单列
```

**归因失败比归因错误好**。宁可标 `unknown` 让用户自己看，也不要错误归因——错误归因会导致后续把 A 软件的缓存当成 B 软件的，进而误判安全等级。

## 9. 输出模型

```go
type PathKind string
const (
    PathKindInstall  PathKind = "install"   // 程序本体
    PathKindCache    PathKind = "cache"     // 可重建的缓存
    PathKindData     PathKind = "data"      // 用户数据（聊天记录、文档）
    PathKindConfig   PathKind = "config"    // 配置、凭据、书签
    PathKindDownload PathKind = "download"  // 下载内容
    PathKindLog      PathKind = "log"       // 日志
    PathKindTemp     PathKind = "temp"      // 临时文件
    PathKindDump     PathKind = "dump"      // 崩溃转储
    PathKindRuntime  PathKind = "runtime"   // 运行时/SDK（如 nvm 的 node 版本、Android SDK）
    PathKindVHD      PathKind = "vhd"       // 虚拟磁盘（*.vhdx/*.vhd）—— 一律 L3 + 迁移
    PathKindSystem   PathKind = "system"    // 系统文件（pagefile/hiberfil/swapfile）—— 一律 L0 + 改设置
    PathKindUnknown  PathKind = "unknown"
)

type PathEntry struct {
    Path        string
    Kind        PathKind
    OwnerAppID  string        // "" = system, "unknown" = 未归因
    OwnerName   string
    OnDisk      int64
    Logical     int64
    FileCount   int64
    Exists      bool
    IsDir       bool
    IsReparse   bool
    ReparseTag  uint32
    LinkTarget  string
    IsOneDrive  bool          // 是否为 OneDrive 管理
    OnCloudOnly bool          // 云占位，本地未下载

    DiscoveredBy string       // knownfolder / env / registry / rule / heuristic
    RuleID       string       // 命中的规则 ID
    Confidence   float64

    // 迁移相关（由 migratability 填充）
    Migratable   bool
    Mechanism    Mechanism
    SuggestedTarget string
}
```
